## Rectification log

### PL-018 — Today doesn't refetch after a foreground sync

- **Severity:** Major
- **Reported as:** Found in code review, while establishing how stale WHOOP strain can be when Today renders.
- **Root cause:** `App.tsx:313-342` fires `syncWhoop()` and `syncHealthConnect()` fire-and-forget on session set and on every `AppState` → `active`. Nothing observes either promise. `TodayScreen`'s focus effect (`TodayScreen.tsx:231-237`) runs `fetchEntries`/`fetchCompositions`/`fetchWorkouts` at mount and on focus, which happens *before* the sync lands. So the first render after foregrounding shows the previous sync's data, and the rows the sync just wrote aren't read until the next focus or a pull-to-refresh. Nothing re-syncs while the app stays foregrounded, so a long session freezes. Measured staleness of the newest cycle row at 13:22 UTC: 60 min (u1, connection-level), 178 min (u2), ~31 h (u3).
- **Affects:** WHOOP workouts today (the only biometric surface Today reads); it will affect the sleep/strain/recovery panel the same way once that ships.
- **Fix:** `src/lib/syncRefetch.ts` watches each sync promise and re-reads once it resolves, if it wrote anything. The syncs stay fire-and-forget: `runSyncs()` returns immediately and the watchers resolve on their own.
  - **Only workouts are re-read.** whoop-sync writes the `whoop_*` tables and health-connect-ingest writes the `biometric_*` tables; neither touches `meal_entries` or `meal_compositions`, so Today's meals and bundles cannot change from a sync. Refetching them would be an unbounded query per foreground for data that provably didn't move. The caller passes the refetch in, so the WHOOP day-score panel joins that one callback later.
  - **Detecting "wrote nothing", so the common foreground costs nothing:** WHOOP reports `skipped: 'throttled' | 'revoked'` (both return before the pull loop) and per-collection `counts`; Health Connect reports per-domain counts. Both are read precisely. Where the answer is genuinely unknown the code refetches rather than guessing: a WHOOP success carrying no counts, a `transient`/`server_error` failure (a collection can fail on page 3 having already upserted pages 1-2, `whoop-sync/index.ts:355-360`), and a Health Connect domain that threw mid-pass. Failures decided before any write (`network_error`, `unauthorized`, `not_connected`, `revoked`, the auth-only codes) skip it.
  - **Health Connect deletions are now counted.** `HealthConnectSyncResult` gains `deletions`, kept separate from `counts` so Settings' "N records synced" is unchanged. Without it a deletion-only pass — a workout deleted in another app arrives as a deletion with zero upserts — was indistinguishable from "nothing happened", and Today kept rendering a workout the database no longer had.
  - **Cost:** at most two refetches per foreground (one per sync that wrote), deliberately not coalesced — WHOOP's pull can take tens of seconds while Health Connect's is local and quick, so making the fast one wait would delay the data reaching the screen, and reusing one in-flight refetch can only return rows read before the second sync's write.
  - **PL-014 (no double report):** a rejected sync is not reported by the watcher — the existing `.catch` at the call site owns that. The store's fetch actions report their own query failures internally and resolve rather than throwing, so the watcher's own catch only fires for an error that escaped unreported, under `todayRefetchAfterSync`.
- **Where:** `<this commit>` — `src/lib/syncRefetch.ts` (new), `src/lib/healthConnectSync.ts`, `App.tsx:315-356`
- **Tests:** `src/lib/__tests__/syncRefetch.test.ts` (18, red first — the module didn't exist), plus a deletion-only case in `healthConnectSync.test.ts`. Sabotage runs: deleting the `skipped` check fails 3 tests; dropping the deletion count fails the deletion test; removing the refetch catch fails the report test. The first sabotage initially PASSED and exposed two vacuous tests — the throttled fixture carried all-zero counts, so it returned false via the wrong branch. Real throttled responses carry no counts at all, and the fixtures now match that.
- **Shipped in:** _not yet published — rides the same OTA as PR 2/PR 3_
- **Verified:** Own device pass, reported by Robbie 2026-09-20: passed on **Pixel and iOS**. Cold start showed workouts without a pull-to-refresh, a foreground inside 15 minutes made no extra call, and data updated after 15. Not yet exercised by a tester, so this stays `Fixed`, not `Verified`.
- **Status:** Fixed

### PL-019 — Dropped WHOOP cycles are never closed or deleted

- **Severity:** Minor
- **Reported as:** Measured on production while checking which cycle maps to "today".
- **Root cause:** `supabase/functions/whoop-sync/index.ts` only ever upserts (blind upserts, `:290-297`); it has no delete or close path (`grep` for `.delete(`/`delete from` returns nothing). A cycle WHOOP later drops or re-scopes stays in `whoop_cycles` with `"end" IS NULL` forever, because the rolling 7-day window (`:492-504`) stops re-pulling it. Measured: u1 has **two** rows with `end IS NULL` — one open 0.8 days (genuine, current) and one open **57.7 days**, last written 81,741 minutes ago. Both surface as `is_current = true` in `biometric_periods_resolved`, so that user has 2 "current" frames.
- **Blast radius today:** contained. `whoop_cycle_nutrition`'s 36-hour guard gives a stale open cycle `effective_end = NULL`, so it owns no meals, and `prev_cycle_contiguous` is false for its successor. The orphan's wake-anchored `local_date` sits 57.7 days in the past, so a date-keyed read is unaffected.
- **Constraint going forward:** **nothing may select "today's cycle" via `is_current`** — including the LLM readiness query. `is_current` is not unique per user and is not a date. Select by wake-anchored `local_date` instead (`biometric_periods_resolved.local_date`).
- **Fix:** _not scheduled. Options: a reconciliation pass that closes or deletes cycles absent from a re-pulled window, or accept and rely on the date-keyed reads plus the constraint above._
- **Status:** Logged

### PL-020 — Batch log alert always says "today's log"

- **Severity:** Minor
- **Reported as:** Found in code review.
- **Root cause:** `BatchesScreen.tsx:103-105`. The eat-time sheet lets the user pick any day, and the branch is on `willBePlanned(chosenAt)` alone: anything not in the future falls to `Alert.alert("Logged", \`${batch.name} added to today's log.\`)`. Picking yesterday 12:00 logs correctly against yesterday but reports "added to today's log".
- **Fix:** New pure helper `batchLogAlert` (`src/lib/batchLogMessage.ts`) builds both the title and the body from the picked instant. The day comes from `formatDayLabel(dateKey(chosenAt))`, so it reads "today's log" only when the pick really is today, "yesterday's log" for yesterday, and "added to the log for Sat 12 Sept" for anything older. The planned branch still mirrors the DB trigger through `willBePlanned`, grace included, so the alert can't contradict what was stored. `BatchesScreen` just renders what the helper returns.
- **Where:** `<this commit>` — `src/lib/batchLogMessage.ts` (new), `src/screens/BatchesScreen.tsx:95-101`
- **Tests:** `src/lib/__tests__/batchLogMessage.test.ts` (7, red first). Sabotage: hardcoding "today's log" again fails 2. One expectation of mine was wrong on first run — Intl's en-GB short month for September is "Sept", not "Sep" — so the test was corrected to match the formatter, not the other way round.
- **Shipped in:** _not yet published — rides the same OTA as PL-018 and PL-021_
- **Verified:** Own device pass 2026-09-20, then **re-confirmed in the combined pass** after Batches returned to the tab bar (the alert is reached from the Batches tab again, not a pushed screen): logging against today, yesterday and an older day each named the right day, and a future pick still read as planned. Not yet exercised by a tester, so this stays `Fixed`.
- **Status:** Fixed

### PL-021 — Today header overflows at 360dp off-today

- **Severity:** Minor
- **Reported as:** Predicted, not yet seen on a device. Computed from the bundled font files (glyph advance widths from `@expo-google-fonts/hanken-grotesk`), not from a render.
- **Root cause:** The header row (`TodayScreen.tsx:804-858`) puts "Return to today" (104.4dp incl. padding and border), the Bundles chip (65.6dp) and the 36dp calendar button in one right-hand group with 6dp gaps — 218dp of a 328dp row at 360dp width. That leaves 110dp for the left block, and the anchor "Wednesday" measures 123.3dp, so the longest weekday wraps. On today's page the same combination fits (220.4dp available, 183.6dp needed for the longest date line).
- **Why it matters now:** adding a Batches button to this row makes it worse, so the reflow is part of the navigation work rather than a follow-up.
- **Fix:** Header reflow. The right-hand row is now three fixed 36dp icon buttons (Bundles when bundles exist and not selecting, Batches, Calendar) — 120dp including gaps at any width. "Return to today" left that row entirely and took the eyebrow's place on off-today pages as a tappable "‹ Today", which costs no extra row height. Measured from the bundled font files at 360dp: the left block is 208dp, against 123.3dp for the longest anchor ("Wednesday") and 183.6dp for the longest date line ("Wednesday 30 September" plus its status dot) — the tightest of the two with 24.4dp spare. Also fits at 375 (iOS floor, 39.4dp spare) and 412. The anchor and date line gained `numberOfLines={1}` + `adjustsFontSizeToFit`, because that 24.4dp runs out at roughly a 1.14x system font scale and shrinking beats wrapping.
- **Where:** `<this commit>` — `src/screens/TodayScreen.tsx` header block and styles
- **Tests:** none — this is layout, and the arithmetic above is font-metric measurement, not a render. It needs the device pass to become a fact.
- **Shipped in:** _not yet published — rides the same OTA as PR 1/PR 3_
- **Verified:** Own device pass, reported by Robbie 2026-09-20: passed, at both densities. The font-metric arithmetic above is now backed by a real render. Not yet exercised by a tester, so this stays `Fixed`.
- **Reflow revised, same day (design review):** the icon-only Bundles and Batches buttons didn't read as anything, so the row is now the **labelled "Bundles" chip plus the 36dp calendar** and Batches went back to the tab bar. What actually fixes PL-021 is unchanged and still in place: "Return to today" living in the eyebrow rather than the icon row. Re-measured at 360dp — chip 65.6 + gap + calendar 36 = 107.6dp, leaving **220.4dp** against the same 183.6dp worst-case date line (36.8 spare, ~x1.17 font scale; 375dp: 51.8 spare; 412dp: 88.8). Needs the combined device pass below to re-confirm.
- **Verified (revised reflow):** combined device pass 2026-09-20 — **Pixel at default density, at 360dp (`wm density 480`) and at the largest system font**, today and off-today, with and without bundles, and in selection mode: no wrap and no overflow, and "‹ Today" returns to today. **iOS** checked at the largest Dynamic Type. The font-metric budget above is now backed by a render on both platforms.
- **Status:** Fixed

### PL-022 — Schema comment describes an upsert gate that doesn't exist

- **Severity:** Polish (documentation only)
- **Reported as:** Found in code review.
- **Root cause:** `supabase/migrations/20260712120000_whoop_data.sql:125-127` says `whoop_updated_at` is "the upsert GATE: only write if theirs is newer than ours". The sync does the opposite and says so: "Upserts are BLIND — no read-then-compare against `whoop_updated_at`" (`whoop-sync/index.ts:290-297`). The code is right and the comment is stale; the practical consequence is that every row's `synced_at` moves on every sync, which is what makes `synced_at` usable as a per-row "last synced" signal.
- **Fix:** _not scheduled. A comment correction on the migration is not worth a migration; fix it in place if that file is edited for another reason, or leave the code comment as the authority._
- **Status:** Logged

## Design change — 2026-09-20, after review

The nav restructure shipped in this round was revised before publishing, on review of the built screens:

- **Batches returns to the tab bar** with its own in-screen header and "+ New". Reaching it through a header icon on Today was not discoverable — neither the Batches nor the Bundles glyph read as anything.
- **Friends leaves the tab bar** for a row in Settings (directly after Sharing), pushed as a root-stack screen with the native header. Its pending-request badge shows in both places — on the Settings tab and on the row — from the same store count, so they cannot disagree.
- Tabs are now Today, History, **Insights** (centre), Batches, Settings. `SOCIAL_ENABLED` moved from TabBar to `src/lib/flags.ts` because it now hides a Settings row rather than a tab; as a result it no longer changes the tab count, so Insights stays centred whatever the flag says. That removes the caveat noted when Insights shipped.
- Kept from the first attempt: the PL-020 alert fix, "‹ Today" in the eyebrow, the typed icon map, and the Insights stub.

**One behaviour change fell out of it.** With Friends pushed from Settings, `CopyConfirm`'s `popToTop()` would have landed a friend-copy on the Settings tab. It now lands on **Today, showing the day the copy went to** (`setViewedDate` then `popTo`) — see PL-001 below.
