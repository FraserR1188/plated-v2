## Rectification log

### PL-035 — Generic whole foods missing from search

- **Severity:** Major. Logging a plain apple is core to a macro tracker. The workaround, creating the food by hand, costs a label's worth of typing for something that has no label.
- **Reported as:** "Unable to locate simple things such as an apple. Instead only shows things like apple juice or apple pie."
- **Root cause:** A feature gap more than a defect, and not reproduced as described.
  - Main search queries only Open Food Facts. It fetches a 50-result page in OFF's own popularity order and re-ranks it locally ([openfoodfacts.ts:347-385](../src/lib/openfoodfacts.ts)). `core_ingredients`, the CoFID staples, is reachable only from the recipe scanner.
  - **Measured 2026-09-25** with the app's exact request and the repo's own ranker: a plain unbranded "Apple" is on today's page at position 12 and ranks #1, and "Cucumber" ranks #1. "Apple pie" isn't on today's page at all. So Ian's page differed from today's, whether by time, data or build. Search failures and results aren't reported anywhere (PL-016), so it can't be traced.
  - The structural gap stands regardless:
    - rarely scanned whole foods fall off a popularity-ordered page;
    - varietal names ("Gala Apples", a whole-word match, +250) lose to "Apple Juice" (a prefix match, +500) by design;
    - OFF produce often carries no nutrition.
  - OFF also returned HTTP 503 to 3 of the first 5 probe requests (see PL-044).
- **Fix:** Agreed 2026-09-25, not started. Two steps, in this order:
  1. **Data step, first.** Remap the `apple` staple from CoFID 14-362 (cooking apple) to CoFID's eating-apple row, with values taken from the CoFID file, never estimated. ~~Seed `unitGrams` for count-eaten produce, so "1 medium apple" can be logged.~~ Dropped on 2026-09-26: there's no citable UK source, and a bare "2 apples" never reaches `unit_grams` anyway (see PL-042 and PL-055). This closes PL-042 on its own, whether or not step 2 lands. **Done 2026-09-26:** PL-042 is Fixed (six remaps, importer run 09:01 BST), so step 2 is unblocked.
  2. **App.** Load `core_ingredients` once per session and match it locally. Show up to 3 staples, whole-word or better, as a "Generic foods" group above the OFF results, including when OFF errors. Details:
     - Selecting a staple goes through the existing ProductScreen → `addEntry` path, with no new insert site.
     - `stapleToProduct` is reused, so a staple missing any of the big four is skipped, never coalesced.
     - **Scope it knowing 27 of 189 staples can't be offered** (MEASURED 2026-09-26 by PL-042's `verify.ts` run):
       - **9 rows** carry a NULL in the big four, all on CoFID codes, where CoFID marks energy/carbohydrate N: black pepper, paprika, cinnamon, turmeric, nutmeg, oregano, and the chicken, vegetable and beef stock cubes (section [1]). `stapleToProduct` returns null for these ([ingredients.ts:159-163](../src/lib/ingredients.ts)), so they never appear in the group.
       - **18 staples** have no live row at all: the ones with no `cofidOverride` (sections [0] and D). Seeding them is a separate decision; a whole-table importer run would insert them as unreviewed guesses.
       - This was predicted in the PL-035 investigation, and is now measured. For those 27, search behaves as it does today.
     - Small-four NULLs stay NULL.
     - `saveIngredient` is **skipped** for `source === "cofid"`: `saved_ingredients` has no provenance column, so a Library re-add would come back mis-credited.
     - Lands with **PL-040** (the attribution mis-credit), which is the same code.
- **Where:** —
- **Shipped in:** — (app change predicted OTA-eligible on both platforms: JS only, runtime fingerprint unchanged. The data step is a service-role importer run, not an app release.)

### PL-036 — AI scan is live-camera only

- **Severity:** Minor. A feature gap: nothing is wrong with what the camera path does.
- **Reported as:** "Couldn't upload screen shot as can only use live camera." The context: "Don't have photo of meal as haven't ordered yet. Planning day around big meal tonight."
- **Root cause:** Feature gap.
  - `captureAndScanMealPhoto` is camera-only by design ([mealPhotoCapture.ts:12-13](../src/lib/mealPhotoCapture.ts)).
  - The photo picker isn't the obstacle. `expo-image-picker` has been in every binary since 2026-07-11. `launchImageLibraryAsync` already ships in CreateFood and the recipe scanner. On Android it uses the system photo picker, with no `READ_MEDIA_*` permission.
  - The obstacle is the prompt. `scan-meal-photo` is written for a plated meal and **tells the model to ignore printed nutrition** (rule 7), and it biases toward home-style portions (rule 5). A menu's printed kcal would be discarded, and a text-only menu would likely come back `no_food`. That's PREDICTED.
- **Fix:** Agreed 2026-09-25, not started.
  - A `mode: "menu"` entry path on the existing `scan-meal-photo`, following `scan-recipe`'s "one function, two entry paths". The tool schema and response contract are unchanged.
  - Menu mode requires the item name (`user_dish_label`) and adds an addendum that uses printed kcal and weight, applies restaurant portions, and estimates the remaining macros.
  - Client: a "From a screenshot or menu" option beside "Take photo".
  - Deploy the Edge Function before the OTA.
- **Where:** —
- **Shipped in:** — (predicted: Edge Function deploy, then OTA on both platforms. The iOS photo-library purpose string is already inaccurate and should be reworded in the next native build.)
- **Verified:** No.
- **Status:** Logged
