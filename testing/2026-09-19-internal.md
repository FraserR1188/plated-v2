## Rectification log

### PL-001 — Friend copy drops sat_fat

- **Severity:** Major
- **Reported as:** Observed. Copying a friend's Asda peanut butter logged sat fat as NULL although the source row had a value.
- **Root cause:** The single-ingredient copy went through `entryToProduct` → ProductScreen, a second rebuild function that had drifted from `draftsFromFeedEntry` and never mapped sat_fat.
- **Fix:** Rerouted through CopyConfirm → `draftsFromFeedEntry` → `applyEntries`; deleted `entryToProduct`. Weightless rows copy with NULL `serving_g`: no 100 g substitution and no refusal. Added guard A (FoodProduct's small four are required-but-undefinable, so omitting one is a compile error) and guard C (value-parity test across every nutrient builder, catches swapped fields).
- **Where:** `fix/friend-copy-one-path` @ `a019c64`, fast-forwarded to master 2026-09-19
- **Shipped in:** OTA, production channel, 2026-09-19. Android group `d3e1e8e4` (runtime `c1907ba4…`), iOS group `e3c46b2e` (runtime `5359dcce…`, matches TestFlight build 3)
- **Verified:** Own device pass: the reproduction now copies sat fat correctly. Needs a tester to copy a friend's single ingredient.
- **Status:** Fixed

### PL-002 — saved_ingredients zero-coerces unknowns

- **Severity:** Major
- **Reported as:** Observed in the schema and write path.
- **Root cause:** `sat_fat/salt/fibre/sugar_per100` were `NOT NULL DEFAULT 0`, and the client wrote `?? 0`, with two read-side coercions on top.
- **Fix:** Migration `20260919120000` drops NOT NULL and DEFAULT 0 on the four columns. There's no type change and no view drop: `sat_fat_per100` stays unconstrained numeric on purpose, because normalising it would mean dropping `saved_ingredients_scored` and risking `security_invoker`. The code removes the `?? 0` write coercion and both read coercions, and unknowns are omitted from the insert. Guard B+ is an AST test that fails any `*_per100` initialiser ending in `?? 0`.
- **Where:** `fix/friend-copy-one-path` @ `a019c64`, fast-forwarded to master 2026-09-19 plus migration `20260919120000`
- **Shipped in:** OTA, production channel, 2026-09-19. Android group `d3e1e8e4`, iOS group `e3c46b2e`. Migration pushed the same day.
- **Verified:** Measured and matched the prediction. The content hash `e8842ac0…` was identical before, after preflight and after the push. 378 rows, 9 users. RLS was clean through both the table and the view on both accounts (235/0 and 5/0). Omitted keys store NULL, and the CHECK still rejects negatives. A tester still needs to save a food with unknown micros.
- **Status:** Fixed

### PL-003 — addEntry swallows insert errors

- **Severity:** Blocker (silent data loss on the create path)
- **Reported as:** Found in code review.
- **Root cause:** `addEntry` (`useStore.ts`) returns `Promise<void>`. On an insert error it reports to Sentry and returns, and with no userId it returns without reporting anything. ProductScreen's create branch, which handles every single-food log (OFF search, AI photo, My Library, barcode, new custom food), can't tell either case from success, so it runs `popToTop()`. The user sees nothing, and on the AI path the recognition and corrections are lost. `saveIngredient` runs before the insert, so a failed log still bumps `use_count` or creates a library row.
- **Fix:** `addEntry` returns the inserted row and throws on both exits, the same way `applyEntries` does. An insert error is reported once inside `addEntry`; a missing user throws without a Sentry report. ProductScreen now runs addEntry → saveIngredient → popToTop. On failure it shows an alert, clears the spinner and keeps every input (on the AI path that includes the recognition and corrections). A saveIngredient failure after a successful insert is caught, so the log stands and the screen closes. A ref guard blocks a double submit. The old test that locked in the silent exit was replaced.
- **Where:** `aca032a` (red tests) and `5abcbcb` (fix), fast-forwarded to master. No PR, because `gh` wasn't installed.
- **Shipped in:** OTA from master @ `48d09e1`, production branch, 2026-09-19 12:37. - **Local checks (measured = predicted):** 580/580 green at baseline; red commit 3 fail / 578 pass for the predicted reasons; fix commit 581/581, tsc 0. `addEntry(` has one caller (`ProductScreen.tsx:563`). 5 sabotage runs, all caught by the intended test. - **Fix:** Done on the branch. `src/components/KeyboardScreen.tsx` is keyboard-controller's `KeyboardAvoidingView` with `behavior="padding"`, `flex: 1`, and offset = explicit prop ?? `HeaderHeightContext` ?? 0. There's no platform branch. `@react-navigation/elements` is now a direct dependency pinned to the installed 2.9.19 (one lockfile line, no new resolution).

Each has a `flex: 1` ScrollView with `keyboardShouldPersistTaps="handled"` and any footer in normal layout. BatchIngredientPicker's quantity view and RecipeScan's body are now ScrollViews; RecipeScan's uses `flexGrow: 1` so the text box still fills the screen.
  - ProductScreen's footer moved from `position: absolute` into normal layout and gained `handled`. The 100/160 spacer that cleared the old footer is now `Spacing.xxl`. The PL-003 submit/guard logic is untouched.
  - Sheets: Today's Save and Apply bundle sheets and LabelConfirmSheet are wrapped with `offset={0}`. LabelConfirmSheet's dimmed backdrop is itself the wrapper.
  - Deleted `ScreenWrapper.tsx` and DeleteAccount's "don't fix this" comment. App.tsx's comment pointing at DeleteAccount now points at the wrapper.
  - A source guard bans `KeyboardAvoidingView` from `"react-native"`. CreateFood is the one allowlisted file until its own PR, which also removes its stale comment. Sign-in screens and Friends are out of scope.
  - Must ship with PL-005 and PL-006.
- **Where:** branch `fix/keyboard-screen-wrapper`: `78a3b8b` (red guard), then `fix(keyboard): lift inputs above the Android keyboard with one KeyboardScreen wrapper`.
- **Local checks (measured = predicted):** On the unmigrated tree the guard was red, 1 failed / 582 passed, naming exactly the six screens that imported RN's KAV. ### PL-006 — BatchEditor Save misses an uncommitted qty

- **Severity:** Major
- **Reported as:** Found in code review.
- **Root cause:** Same shape as PL-005. IngredientRow qty commits on blur, and the header Save is always reachable. This can already happen today.
- **Fix:** Done on the branch. IngredientRow commits on change, the same live-text pattern as PL-005, through the shared `parseGrams`. Every committed quantity still goes through `updateBatchIngredientQuantity`, which clears yield and portion (YIELD-ON-EDIT), so Save disables as soon as a new quantity is typed and can't write new ingredients against the old yield. Text that doesn't parse keeps the last good quantity and reverts on blur. Two visible side effects:
  - The "Ingredients changed" banner now appears while typing, not on blur.
  - Focusing a qty field and leaving it unchanged no longer clears the yield. The old blur always re-committed.
- **Where:** branch `fix/keyboard-screen-wrapper`: `2a83c62` and `a09d9ed` (shared `parseGrams`, red then green), then `fix(batches): save the quantity in the box, not the last-blurred value`.
- **Local checks (measured = predicted):** Suite 588/588, tsc 0. As with PL-005, the race is event wiring and isn't covered by a Vitest test; the device check covers it.
- **Shipped in:** OTA from master @ `4c2d2f1`, 2026-09-19 13:33 BST. Android group `ce5de6bb-f335-4679-922b-c55786c6f893` (runtime `c1907ba4…`), iOS group `bf4b3ef8-467f-4909-a00d-657bec5c4df8` (runtime `5359dcce…`).
- **Device pass (2026-09-19, Pixel, dev client on `fix/keyboard-screen-wrapper` @ `dc56dd3`):** every checklist surface passed.
- **Behaviour change, accepted by Robbie (2026-09-19):** typing a quantity clears yield and portion immediately, so Save stays disabled until both are re-entered. Reverting the quantity does not restore them. `updateBatchIngredientQuantity` (`useStore.ts:1401-1411`) blanks both on every call and keeps no previous value; the old commit-on-blur did the same. They come back only if they're typed again, or if the editor is left without saving. The suggestion chip offers the raw ingredient total for yield, not the old value. Leaving discards the draft, and reopening a saved batch reloads its stored yield and portion (`BatchEditorScreen.tsx:208-209`).
- **Verified:** Not yet. A tester needs to edit a batch quantity and save after the OTA.
- **Status:** Fixed

### PL-007 — CSV and last30Days use UTC dates

- **Severity:** Major
- **Root cause:** `csv.ts` uses `toISOString().slice(0,10)` next to a local-time column, so a meal at 00:30 BST exports under the previous day. `last30Days` computes its range in UTC too. Both break the dateKey invariant.
- **Fix:** Planned. Use the shared `dateKey` helper for both.
- **Status:** Logged

### PL-008 — CSV exports NULL as 0.0

- **Fix:** Planned. Export an empty cell for NULL.
- **Status:** Logged

### PL-009 — Float noise in stored small four

- **Severity:** Polish
- **Root cause:** JS multiplication (`0.62 × 3 = 1.8599999999999999`) is sent verbatim into unconstrained numeric columns. Only the small four show it, because the `numeric(8,2)` columns round on the way in.
- **Decision:** Won't fix. `compositions.ts` deliberately rounds only at the point of display. The noise never shows in the UI or CSV, never creates or removes a NULL, and can't move a correlation coefficient.
- **Constraint going forward:** SQL in the readiness query and pairing views must not hash, `DISTINCT` or equality-join on `::text` casts of the small four.
- **Status:** Won't fix
