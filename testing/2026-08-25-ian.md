## Rectification log

**`af371df` doesn't fix these.** Its message (26 Aug) says "tester reports P-TF01/P-TF02 fixed", but it only changes `package.json` and `package-lock.json`, adding `expo-updates`. The real changes are the commits named below. All of them are ancestors of master.

### P-TF01a — Confirmation email never arrived

- **Severity:** Minor. Ian wasn't blocked: "Nothing happened so going to move onto next stage and scan something". It would become a Blocker if Confirm email were turned on and the email didn't arrive, because sign-in then fails with `email_not_confirmed`.
- **Reported as:** Ian expected to "Receive an email after creating account"; "Nothing happened".
- **Root cause:** Email confirmation is off on the Supabase project, so no confirmation email is sent to anyone. Measured 2026-09-19: the project's `/auth/v1/settings` returns `mailer_autoconfirm: true`. `87e16cf` (26 Aug) records that it was already off then, which made the app's "check your email to confirm" copy false.
- **Fix:** Not fixed.
  - `87e16cf` corrected the false copy.
  - `26a696c` and `8eb2e5e` added a confirm-email deep link and a "pending" screen with a resend button. That flow stays dormant while confirmation is off.
  - `8eb2e5e` also shows the pending screen ("Check your email … we've sent a confirmation link") after every successful sign-up: `App.tsx`'s `handleSubmit` calls `enterPending` whatever `signUp` returns. With confirmation off, `signUp` also returns a session, which should switch the app to the navigator first, so the screen probably never shows. That hasn't been checked on a device. If it does show, it's the same false promise Ian got.
  - Deciding check: sign up a new account on the current build. If the app goes straight in and nothing promises an email, this becomes Fixed. If "Check your email" appears, it's Major and `enterPending` needs to depend on there being no session.
- **Where:** `87e16cf`, `26a696c`, `8eb2e5e`.
- **Shipped in:** `87e16cf` has been in every Android store build since v8 (`af371df`, 26 Aug). `26a696c` and `8eb2e5e` are newer than v10 (`5dde876`), so v11 (`bff36d6`, 5 Sep) is the first Android store build with them. All three are in iOS build 3 (`950a276`).
- **Verified:** No.
- **Status:** Logged

### P-TF01b — Never asked for targets

- **Severity:** Major. Every account starts on the defaults and the day's rings measure against them until the user finds Settings: wrong numbers, with a workaround.
- **Reported as:** Ian expected "to fill in macros and calorie targets" after creating an account.
- **Root cause:** There's no onboarding step; targets can only be set in Settings. Sign-up (`handle_new_user`, `20260819101000_profile_on_signup.sql`) creates a `profiles` row but no `goals` row. `fetchGoals` keeps the client's `DEFAULT_GOALS` (`useStore.ts`: 2000 kcal, 150 g protein, 200 g carbs, 65 g fat, sat fat 20, salt 6, fibre 30, sugar 30) until a row exists. Its `.single()` should also report a "no rows" error to Sentry on every fetch for such a user. That last part is predicted from the code, not checked in Sentry.
- **Fix:** None found. No commit since 25 Aug touches onboarding or target setup.
- **Where:** —
- **Shipped in:** —
- **Verified:** No.
- **Status:** Logged

### P-TF02a — Repeated search errors

- **Severity:** Major. Search worked, but only after several retries.
- **Reported as:** "Kept coming up with an error and a try again button. After numerous clicks it searched."
- **Root cause:** Unconfirmed. In `f48184c`, the newest store build at the time, any failed `searchFood` showed "Couldn't search … Tap to retry". There was no timeout and no `res.ok` check, so the error was either a network failure or `res.json()` failing on a non-JSON body, such as an Open Food Facts error or rate-limit page. Nothing reported the failure or kept a status code, so it can't be tied to rate limiting. Search failures still aren't sent to Sentry, so a repeat wouldn't be visible either.
- **Fix:** Probable fix, unconfirmed. `e958f4d` (26 Aug) sends a User-Agent, because Open Food Facts rate-limits anonymous search more heavily, and adds a 10 s timeout. The User-Agent fits Ian's symptom if the failures were rate limiting. The timeout doesn't fix errors; it turns a hung request into one.
- **Where:** `e958f4d`.
- **Shipped in:** Every Android store build since v8 (`af371df`, 26 Aug), and iOS build 3 (`950a276`).
- **Verified:** No. Ian's symptom isn't tied to the timeout or the User-Agent.
- **Status:** Logged

### P-TF02b — Search seems to need a trailing space

- **Severity:** Minor. Ian flagged it as "maybe coincidence".
- **Reported as:** "Also sometimes seems to need a space after the item name, maybe coincidence."
- **Root cause:** Unconfirmed. A trailing space can't change what's searched: `handleSearch` and `searchFood` both trim before the request, then and now. What typing a space does do is restart the 600 ms debounce and send the same search again. That's a retry, and with P-TF02a's intermittent failures it would look like "sometimes needs a space". Not reproduced.
- **Fix:** None found.
- **Where:** —
- **Shipped in:** —
- **Verified:** No.
- **Status:** Logged
