## Rectification log

### PL-050 — `fetchEntries` truncates silently at the API's row cap

- **Severity:** Major.
  - Nothing errors. Past the cap, the oldest-logged rows just stop reaching the store.
  - Today/History show those days as empty, the 30-day CSV can come out short, and a long-pending plan can miss the confirmation banner.
  - It's the wrong-numbers class, and invisible to the user.
- **Reported as:** Found in code review. The receipt-scanner investigation (`docs/2026-09-25-receipt-scanner-findings.md`, candidate C) noted `fetchEntries` has no range while `supabase/config.toml` sets `max_rows = 1000`.
- **MEASURED 2026-09-26:**
  - User A has 787 rows, at 8.4/day since 2026-06-24.
  - At that rate A crosses 1000 around 2026-10-21, if hosted Max rows = 1000. That setting wasn't confirmed at the time of measuring.
  - **Stopgap, same day:** hosted Max rows raised from 1000 to 2000 in the dashboard (no deploy). User A now crosses around mid-February 2027.
- **Root cause:** Confirmed from the code.
  - `fetchEntries` ran `select("*").eq("user_id", …).order("logged_at", desc)` with no `.range()` ([useStore.ts:638-649](../src/store/useStore.ts) at `177ed0a`).
  - PostgREST answers that with at most `max_rows` rows and no error, so the store held the newest `max_rows` rows as if they were all of them.
  - The order also had no unique tiebreaker. A bundle apply inserts several rows with one `logged_at`, so any paging on that order alone would read tied rows twice or not at all across a page boundary.
- **Fix:**
  - Page with `.range()` until a short page returns.
  - Order by `logged_at desc, id desc`, so every row has one fixed position and pages can't overlap or skip.
  - Page size is `ENTRIES_PAGE_SIZE`, below `max_rows` and pinned there by a test that reads `supabase/config.toml`.
  - A failed page throws inside the pager. `fetchEntries` reports it once and keeps the previous list: a partial list is never installed as if complete (the PL-003 rule).
  - Local `max_rows` set to 2000 to match hosted.
- **Where:** master @ `be8ed92` (red tests + filing) + `eec75b9` (fix). Code: `src/lib/paging.ts` (`fetchAllPages`), `src/store/useStore.ts` (`ENTRIES_PAGE_SIZE = 500`, `fetchEntries`), `supabase/config.toml` (`max_rows = 2000`).

### PL-052 — `passata` is a homemade tomato sauce, and a staple can't be deleted

- **Severity:** Major. Wrong numbers, live in the recipe scanner.
- **Reported as:** Found in PL-042's step-1 review.
- **Root cause:**
  - `scripts/seedStaples.ts:264` pins `passata` (aliases `sieved tomatoes`, `tomato sauce`) to 17-834, "Sauce, tomato based, homemade". That row is 70 kcal and 4.5 g fat per 100 g: a cooked sauce with added fat, not sieved tomatoes.
  - `cofid.csv` has no passata row, so any code chosen here is wrong. The honest state is no staple, which lets the line fall through to OFF, the same reasoning as chicken in 1428e57.
  - Removing the entry from `SEED_STAPLES` isn't enough. The importer only upserts: a slug that leaves the list keeps its live row, and a staple hit short-circuits the OFF tier.
- **Fix:** Candidate, not started.
  - Give the importer a delete path for slugs no longer in `SEED_STAPLES`: either a reconcile step or an explicit `--delete slug`, dry-run first.
  - Then remove `passata`.
  - No chicken cleanup is needed alongside it. PL-042's drift check (2026-09-26 08:30, section C empty) showed `chicken-breast`/`chicken-thigh` aren't live, so 1428e57's removal took effect. `passata` is the only known slug that needs the delete path.

### PL-053 — `pepper` resolves to either pepper staple

- **Severity:** Minor. PREDICTED, not reproduced: a recipe line reading just "pepper" can resolve to the wrong food.
- **Reported as:** Found in PL-042's step-1 review.
- **Root cause:**
  - `bell-pepper` (`seedStaples.ts:135`) and `black-pepper` (`:155`) both carry the alias `pepper`.
  - `lookupStapleFromDb` ([ingredients.ts:281-300](../src/lib/ingredients.ts)) runs `.or(slug / aliases / display_name).limit(1).maybeSingle()` with no ORDER BY, so which of the two comes back is whatever order Postgres returns. An upsert rewrites both rows, so that order can change after any importer run.
  - Separately, `bell-pepper` is CoFID's red pepper (13-524) but carries the alias `green pepper`. Green is its own row (13-318, 15 kcal against red's 21).
- **Fix:** Candidate, not started. Take `pepper` off at least one of the two staples, and move `green pepper` off the red row (drop it, or give it its own staple). Whether the lookup should also get a deterministic order is a resolver change, which belongs to PL-035.

### PL-055 — Produce count weights are unsourced estimates

- **Severity:** Major. They scale every counted recipe-scanner line that resolves to one of these staples.
- **Reported as:** Found in PL-042's step-1 review.
- **Root cause:**
  - These `unit_grams` weights have no stated source. The file's own header calls every seeded value "ESTIMATES, not facts" and lists produce counts under "REVIEW FOCUS":

    | slug | `unit_grams` | line |
    |---|---|---|
    | onion | small 90, medium 130, large 200 | `seedStaples.ts:127-128` |
    | tomato | small 90, medium 120, large 180, cherry 17 | `:129-130` |
    | carrot | small 50, medium 61, large 72 | `:131-132` |
    | potato | small 130, medium 170, large 300 | `:133-134` |
    | bell-pepper | medium 120, large 160 | `:135-136` |
    | lemon | medium 58 | `:139-140` |
    | lime | medium 67 | `:141-142` |
    | banana | small 90, medium 118, large 140 | `:143-144` |

  - `estimateGrams` ([ingredients.ts:96-119](../src/lib/ingredients.ts)) multiplies the count by these whenever the scanned unit is a size word. That's labelled 'estimated', but the number is still prefilled.
  - **Evidence they weren't measured:** a medium lime (67 g) is heavier than a medium lemon (58 g).
  - They're also inconsistent with the file's own rule that count weights are edible portion. PL-042 moves `lime` to flesh only (14-131), so any whole-lime weight would now be multiplied against flesh-only values.
- **Fix:** Undecided. Two options:
  - **Remove them.** Set `unit_grams` to `{}` for these eight via an `--only` run. A counted line then comes back `grams: null`, and the confirm step forces a weight, which is the designed safe state. The cost is one typed weight per counted produce line.
  - **Source them.** Take each weight from a citable UK portion source (FSA *Food Portion Sizes*; not on hand) on an edible-portion basis, and record the source per row.
  - Recommendation: remove now and reinstate row by row as sources are found. A sourced weight can come back in without a schema change.
  - Open: the same question applies to the other seeded values outside this list (egg sizes, garlic clove/bulb, the spoon weights, densities).

### PL-056 — `fetchWorkouts` truncates arbitrarily at the API's row cap

- **Severity:** Major.
  - It's the same silent cap as PL-050, with a worse failure shape. `fetchWorkouts` had **no ORDER BY**, so past `max_rows` the workouts it lost weren't the oldest but whichever the planner put last.
  - That can include today's, and it can differ from one refresh to the next.
  - Nothing errors.
- **Reported as:** Found in PL-050's sweep of per-user selects, where it was the highest-risk candidate. Filed on the user's instruction, 2026-09-26.
- **Rows:** not measured. About one row per workout per source, and Health Connect can backfill history (`READ_HEALTH_DATA_HISTORY`).
- **Root cause:** Confirmed from the code.
  - `fetchWorkouts` ran `select("*").eq("user_id", …)` with no `.order()` and no `.range()` ([useStore.ts:691-698](../src/store/useStore.ts) at `a113f22`).
  - A workout's identity in `biometric_workouts` is `(origin_package, source_workout_id)`. This is the view's own composite key ([20260830160000_biometric_workouts_dedup.sql:257-266](../supabase/migrations/20260830160000_biometric_workouts_dedup.sql)), matching `biometric_workout_sessions`' primary key per user and `whoop_workouts.id` on the WHOOP arm.
  - Two apps can log workouts starting in the same second, and one app can log two, so no shorter key is total.
- **Fix:**
  - Page with `fetchAllPages` (PL-050), ordered `workout_start desc, origin_package, source_workout_id`.
  - `WORKOUTS_PAGE_SIZE` below `max_rows`, pinned by test.
  - A failed page keeps the previous workouts and reports once, from `fetchWorkouts`, as with PL-050.
- **Where:** master @ `fe61583` (red tests + filing) and the fix commit that follows it. Code: `src/store/useStore.ts` (`WORKOUTS_PAGE_SIZE = 500`, `fetchWorkouts`), test helper `src/store/__tests__/helpers/fakePostgrest.ts`.
- **Local checks (MEASURED 2026-09-26):**
  - **Red at `fe61583`**, against the unordered, unpaged select and a fake capped at 1000 rows:
    - 1000 of 2,350 workouts held;
    - 203 missing in the shared-start test;

  - **Fixture corrected in the fix commit.**
    - At `fe61583`, tied blocks were 4 rows, and 500 / 4 is whole, so no tie ever straddled a page boundary. Tiebreaker sabotages then failed only on order, never on duplicates or drops.
    - Blocks are now 7 rows with packages cycling mod 3, so rows sharing start **and** package straddle every boundary.
    - The corrected test was re-run against `fe61583`'s `useStore.ts`: still red on all 5 tests, with the same figures as above.
  - **Green after the fix:** the new tests pass 5/5. The full suite passes **1045/1045 across 56 files**. `tsc --noEmit` reports 0 errors. `fetchEntriesPaging.test.ts` is unchanged and green.
  - **Sabotage 1, `source_workout_id` tiebreaker removed:** the shared-start test goes red with `{ duplicates: 2, missing: 2 }`. The 2,350 test goes red at 2,348 unique. Restored, identical, green.
  - **Sabotage 2, both tiebreakers removed (start only):** red with `{ duplicates: 2, missing: 2 }`, and 2,344 unique of 2,350. Restored, identical, green.
  - **Sabotage 3, shared pager returns after the first page:** 500 of 2,350 held; 703 missing in the shared-start test. The failed-page test also goes red, because a 500-row partial list replaced the previous one. Restored, identical, green.
