## 1. Keyboard covering inputs

### Root cause
- **What Android does today:** app.json doesn't set `softwareKeyboardLayoutMode`, so Expo writes `adjustResize` ([WindowSoftInputMode.js:38-44](../node_modules/@expo/config-plugins/build/android/WindowSoftInputMode.js#L38-L44)). Edge-to-edge is on by default ([withEdgeToEdge.js:50-54](../node_modules/expo/node_modules/@expo/cli/node_modules/@expo/prebuild-config/build/plugins/unversioned/edge-to-edge/withEdgeToEdge.js#L50-L54)), and RN 0.81 targets SDK 36, where it can't be turned off.
  - Under edge-to-edge, `adjustResize` no longer shrinks the window. The keyboard just draws over it.
  - So the whole app gets no native layout change. Any screen that doesn't read the keyboard's inset itself gets covered.
- **It was already fixed once, for sign-in only.** Commits 51c3de1 → 6a57aae → c9208a4 (2026-08-26) diagnosed this and fixed AuthScreen with `react-native-keyboard-controller`. They flagged DeleteAccount as a follow-up that never happened.
  - `KeyboardProvider` is already at the root ([App.tsx:374](../App.tsx#L374)), and the library's native module is already in the binary.
- **One correction to that record.** 6a57aae says RN's stock `KeyboardAvoidingView` "measures Android's keyboard height as 0". RN 0.81 actually reports the IME inset minus the system-bar inset, which isn't 0 ([ReactRootView.java:890-926](../node_modules/react-native/ReactAndroid/src/main/java/com/facebook/react/ReactRootView.java#L890-L926)). What failed on device was `behavior={undefined}` on Android, which does nothing by design. This doesn't change the recommendation.

### iOS/Android divergence
- **The repo's pattern is the pre-edge-to-edge idiom (7 screens).** iOS never resized, so it used padding. Android resized natively, so the component was switched off to avoid a double lift, which is exactly what [DeleteAccountScreen.tsx:101-105](../src/screens/DeleteAccountScreen.tsx#L101-L105) says ("don't 'fix' this into a value"). At targetSdk 36 the Android half is just off.
- **`padding` vs `height`: use `padding` on both platforms, with no `Platform.OS` branch.** keyboard-controller's `height` behaviour freezes the size measured at layout and forces `flex: 0` ([index.tsx:122-160](../node_modules/react-native-keyboard-controller/src/components/KeyboardAvoidingView/index.tsx#L122-L160)), which fights `flex: 1` layouts. `padding` is what the three device-validated screens use.
- **`keyboardVerticalOffset`: this is where screens actually differ.**
  - keyboard-controller computes the lift from its own layout frame, which is relative to its parent ([index.tsx:101-108](../node_modules/react-native-keyboard-controller/src/components/KeyboardAvoidingView/index.tsx#L101-L108)). It under-lifts by exactly the distance between the screen top and where it starts.
  - On Android that only matters on the three native-header screens (CopyConfirm, BundleApplyReview, DeleteAccount): offset = header height. Tab screens and screens that draw their own header start at 0.
  - The real platform difference is iOS-only. `presentation: "modal"` is a page sheet with a top gap on iOS but a full-screen push on Android. iOS modal screens would need an extra offset. I can't verify that while iOS is paused, so I'm flagging it rather than guessing a number.
- **DateTimeField precedent:** it gives callers one contract and keeps the platform branch inside the component. The same shape works here one level up. keyboard-controller already hides the platform split for the lift itself. A wrapper would hide the one remaining per-screen variable, the offset, so no screen passes `Platform.OS` or a hard-coded number.

### One wrapper? Yes, with three caveats
- **Shape:** keyboard-controller's `KeyboardAvoidingView`, `behavior="padding"`, `flex: 1`, with the offset read from `useContext(HeaderHeightContext) ?? 0` and an explicit override.
  - Use the context rather than `useHeaderHeight()`, which throws outside a navigator. That keeps the wrapper safe on the sign-in screens.
  - native-stack puts 0 in that context when `headerShown: false` ([NativeStackView.native.tsx:435-438](../node_modules/@react-navigation/native-stack/src/views/NativeStackView.native.tsx#L435-L438)).
  - It needs `@react-navigation/elements` as a direct dependency. It's already installed transitively at 2.9.19 and is pure JS.
- **Each screen's side:** a `ScrollView` (`flex: 1`, `handled`) plus a footer in normal layout, inside the wrapper.
- **Scrolling the field into view:** RN's `ScrollView` resize handler calls through to Android's own, which scrolls the focused child back into view when the viewport shrinks ([ReactScrollView.java:372](../node_modules/react-native/ReactAndroid/src/main/java/com/facebook/react/views/scroll/ReactScrollView.java#L372)). So `KeyboardAwareScrollView` shouldn't be needed (predicted).

The caveats:
1. **ProductScreen:** its footer is `position: absolute; bottom: 0` ([ProductScreen.tsx:1801](../src/screens/ProductScreen.tsx#L1801)). I don't expect it to follow a padding lift (not verified). Either way, turning it into a normal footer like CopyConfirm's removes the question. That's a layout change, not just a wrap.
2. **CreateFood:** wrapping it as it stands would double-lift. Adopting the wrapper means deleting its own keyboard-height padding. It's the one in-app screen that probably works today, so migrate it last with a before/after device check.
3. **Modal sheets:** keyboard-controller 1.18.5 attaches to Modal windows ([ModalAttachedWatcher.kt](../node_modules/react-native-keyboard-controller/android/src/main/java/com/reactnativekeyboardcontroller/modal/ModalAttachedWatcher.kt)), and RN 0.81 forces Modals edge-to-edge too, so the wrapper works inside a sheet. But `HeaderHeightContext` passes through the Modal portal, so a sheet would inherit its host screen's header height. All current hosts are 0; sheets should still force `offset={0}`.

None of the 17 needs a second mechanism.

### Recommendation and blast radius
One `KeyboardScreen` wrapper as described above.

- **New:** the component, plus `@react-navigation/elements` in package.json.
- **Mechanical wrap or swap (9):** CopyConfirm, BundleApplyReview, DeleteAccount (drop the stale comment), AddIngredient, BatchEditor, BatchIngredientPicker, RecipeScan, RecipeConfirm, Settings.
- **Structural (2):** ProductScreen (footer into normal layout, add `handled`) and CreateFood (remove its own padding logic).
- **Sheets (2 files, 3 sheets):** TodayScreen, LabelConfirmSheet.
- **Optional, same behaviour:** the three sign-in screens and Friends, for one path.
- **Must ship with it:** the BundleApplyReview fix under "Other bugs" below. Lifting its footer makes that race reachable in normal use.
- **Delivery:** it's all JS and the native module is already in the binary, so it should be OTA-eligible. Confirm the fingerprint is unchanged before assuming that.

### Testing
**Device-only.** The lift depends on native keyboard insets, Reanimated on the UI thread, layout and the native ScrollView. None of that exists in Vitest's `node` environment, and RNTL wouldn't run native layout either. I'm not proposing a behaviour test.

The one honest Vitest piece is optional: a source-level guard like `noRawHexColors` that fails if anything imports `KeyboardAvoidingView` from `"react-native"`. It stops a screen sliding back to the old pattern; it proves nothing about the keyboard.

Device check for each surface:
- Focus the lowest input: the field and the footer should sit above the keyboard.
- With the keyboard up, the first tap on the footer should register.
- On header screens, there should be no gap and no under-lift.

## 2. Float noise (log only)
- **Mechanism:** JS multiplies to the nearest double, e.g. `0.62 × 3 = 1.8599999999999999` (reproduced in Node). `JSON.stringify` sends that exact decimal. Unconstrained `numeric` stores it as sent, while `numeric(8,2)` rounds it on the way in, so only the small four show it. `3.1 × 3.22` also gives `9.982000000000001`; that's just one pair that reproduces it, not necessarily your real inputs.
- **It isn't new with the reroute.** Rounding is deliberately absent everywhere ([compositions.ts:620-623](../src/lib/compositions.ts#L620-L623): "round only at the point of display"). It enters at:
  - `scaleMacros` ([compositions.ts:601-614](../src/lib/compositions.ts#L601-L614)), used by friend copy with changed grams and by bundle rescale, then passed straight through `applyEntries` ([entries.ts:103-106](../src/lib/entries.ts#L103-L106)).
  - ProductScreen's own create and edit writes, `draft.salt_per100 * f` ([ProductScreen.tsx:509-512](../src/screens/ProductScreen.tsx#L509-L512)). An ordinary 150 g log of 1.24 g/100 g salt stores the same `1.8599999999999999`.
  - `meal_composition_items` has all eight columns unconstrained ([meal_bundles.sql:95-103](../supabase/migrations/20260713120000_meal_bundles.sql#L95-L103)), so bundle and batch items can carry noise in the big four too until `meal_entries` rounds them.
- **Downstream:**
  - **App UI:** never visible. Every render formats the value first (`roundSalt`, `toFixed`, `computeServingTotals`, History's averages).
  - **CSV:** never visible (`toFixed` throughout).
  - **Supabase dashboard / raw SQL:** visible, cosmetic only.
  - **Correlation views:** they only `sum()` and `count()` the small four, with no equality, threshold or rounding logic. The error is about 1e-16 relative, so it can't move a coefficient. `0 × r` is exactly 0, so noise never creates or removes a NULL, never changes the known-meal counts, and never flips a sign (so the negatives CHECK is unaffected).
  - **Latent risk:** anything that compares these values as text in future, such as `md5(string_agg(::text))` hashes, `DISTINCT`, or equality joins. Your verify hash compares the same rows before and after, so it's unaffected.
  - `MacroBar`'s strict `consumed > goal` is a hair-trigger at exact equality, but that comes from summing floats in memory (`0.1+0.2 > 0.3` is already true), not from storage.
- **Verdict: cosmetic.**

## 3. addEntry swallowed errors (log only)
- **Scope after the reroute:** exactly one caller, ProductScreen's create branch ([ProductScreen.tsx:553](../src/screens/ProductScreen.tsx#L553)). That branch is every single-food log in the app:
  - OFF search ([AddIngredientScreen.tsx:138](../src/screens/AddIngredientScreen.tsx#L138))
  - AI meal photo (`:171`)
  - My Library (`:186`)
  - barcode ([ScannerScreen.tsx:101](../src/screens/ScannerScreen.tsx#L101))
  - new custom food ([CreateFoodScreen.tsx:561](../src/screens/CreateFoodScreen.tsx#L561))

  Editing goes through `updateEntry` ([TodayScreen.tsx:310-317](../src/screens/TodayScreen.tsx#L310-L317)), which already reports errors. Friend copies, copy-a-day, bundles and batches all use `applyEntries`, which throws and whose callers show an alert.
- **Two silent exits** ([useStore.ts:697-754](../src/store/useStore.ts#L697-L754)). The function returns `Promise<void>`, so the caller can't tell either way.
  - `!userId` returns with no report at all. It's practically unreachable from ProductScreen.
  - An insert error calls `reportError` (Sentry, level `error`, fingerprint `addEntry`) and returns.
- **What the user sees on failure:** a spinner, then `popToTop()` closes the whole flow back to Today. There's no alert and no toast. The item just isn't there, because the store only adds it on success. Retrying means searching or scanning again; on the AI path the recognition and any corrections are lost.
- **Side effects that already happened:**
  - `saveIngredient` runs before the insert ([ProductScreen.tsx:552](../src/screens/ProductScreen.tsx#L552)). It bumps `use_count` or creates a library row, so the food ranks higher in My Library as though it had been logged.
  - On the CreateFood path, the custom food and its photos are already saved (harmless).
- **Size:** it covers the main logging path. How often it actually fails is in Sentry under the `addEntry` issue; that's the number to pull before deciding priority.

## Other bugs found (not fixed)

1. **BundleApplyReview grams race** (plausible). Grams only commit to the store on blur/submit ([BundleApplyReviewScreen.tsx:84-92](../src/screens/BundleApplyReviewScreen.tsx#L84-L92)), and Confirm reads the store. Tapping the footer doesn't blur the field, so the last committed grams get applied. It was already on the open-items list. The keyboard fix makes it reachable in normal use. CopyConfirm's live-text approach is the in-repo fix.
2. **BatchEditor has the same shape.** `IngredientRow` qty commits on blur, but header Save is always reachable. Reachable today.
3. **CSV export date is UTC** ([csv.ts:26](../src/lib/csv.ts#L26), `toISOString().slice(0,10)`), paired with a local-time column. A meal at 00:30 BST exports under the previous day. `last30Days` also uses UTC for its range. Both break the `dateKey` invariant.
4. **CSV exports NULL small-four as `0.0`** ([csv.ts:41-44](../src/lib/csv.ts#L41-L44)). That breaks NULL-not-zero in the export.
5. **Stale comments:** [DeleteAccountScreen.tsx:101-105](../src/screens/DeleteAccountScreen.tsx#L101-L105) actively tells readers to keep the bug. [CreateFoodScreen.tsx:8-15](../src/screens/CreateFoodScreen.tsx#L8-L15) still describes window resize.
6. **Dead code:** [ScreenWrapper.tsx](../src/components/ScreenWrapper.tsx) has no imports, and it would be easy to confuse with the new wrapper.
7. **RecipeConfirm doubles the bottom inset** (cosmetic): `SafeAreaView edges={["bottom"]}` plus the footer's own `insets.bottom`.
