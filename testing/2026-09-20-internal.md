## Rectification log

### PL-018 — Today doesn't refetch after a foreground sync

- **Severity:** Major
- **Reported as:** Found in code review, while establishing how stale WHOOP strain can be when Today renders.
- **Root cause:** `App.tsx:313-342` fires `syncWhoop()` and `syncHealthConnect()` fire-and-forget on session set and on every `AppState` → `active`. Nothing observes either promise. `TodayScreen`'s focus effect (`TodayScreen.tsx:231-237`) runs `fetchEntries`/`fetchCompositions`/`fetchWorkouts` at mount and on focus, which happens *before* the sync lands. So the first render after foregrounding shows the previous sync's data, and the rows the sync just wrote aren't read until the next focus or a pull-to-refresh. Nothing re-syncs while the app stays foregrounded, so a long session freezes. Measured staleness of the newest cycle row at 13:22 UTC: 60 min (u1, connection-level), 178 min (u2), ~31 h (u3).
- **Affects:** WHOOP workouts today (the only biometric surface Today reads); it will affect the sleep/strain/recovery panel the same way once that ships.
- **Fix:** `src/lib/syncRefetch.ts` watches each sync promise and re-reads once it resolves, if it wrote anything. The syncs stay fire-and-forget: `runSyncs()` returns immediately and the watchers resolve on their own.
  - **Only workouts are re-read.** whoop-sync writes the `whoop_*` tables and health-connect-ingest writes the `biometric_*` tables; neither touches `meal_entries` or `meal_compositions`, so Today's meals and bundles cannot change from a sync. Refetching them would be an unbounded query per foreground for data that provably didn't move. The caller passes the refetch in, so the WHOOP day-score panel joins that one callback later.
  - **Detecting "wrote nothing", so the common foreground costs nothing:** WHOOP reports `skipped: 'throttled' | 'revoked'` (both return before the pull loop) and per-collection `counts`; Health Connect reports per-domain counts. Both are read precisely. Where the answer is genuinely unknown the code refetches rather than guessing: a WHOOP success carrying no counts, a `transient`/`server_error` failure (a collection can fail on page 3 having already upserted pages 1-2, `whoop-sync/index.ts:355-360`), and a Health Connect domain that threw mid-pass. Failures decided before any write (`network_error`, `unauthorized`, `not_connected`, `revoked`, the auth-only codes) skip it.
  - **Health Connect deletions are now counted.** `HealthConnectSyncResult` gains `deletions`, kept separate from `counts` so Settings' "N records synced" is unchanged. Without it a deletion-only pass — a workout deleted in another app arrives as a deletion with zero upserts — was indistinguishable from "nothing happened", and Today kept rendering a workout the database no longer had.
  - **Cost:** at most two refetches per foreground (one per sync that wrote), deliberately not coalesced — WHOOP's pull can take tens of seconds while Health Connect's is local and quick, so making the fast one wait would delay the data reaching the screen, and reusing one in-flight refetch can only return rows read before the second sync's write.
  - **PL-014 (no double report):** a rejected sync is not reported by the watcher — the existing `.catch` at the call site owns that. The store's fetch actions report their own query failures internally and resolve rather than throwing, so the watcher's own catch only fires for an error that escaped unreported, under `todayRefetchAfterSync`.
- **Where:** `<this commit>` — `src/lib/syncRefetch.ts` (new), `src/lib/healthConnectSync.ts`, `App.tsx:315-356`
- **Tests:** `src/lib/__tests__/syncRefetch.test.ts` (18, red first — the module didn't exist), plus a deletion-only case in `healthConnectSync.test.ts`. Sabotage runs: deleting the `skipped` check fails 3 tests; dropping the deletion count fails the deletion test; removing the refetch catch fails the report test. The first sabotage initially PASSED and exposed two vacuous tests — the throttled fixture carried all-zero counts, so it returned false via the wrong branch. Real throttled responses carry no counts at all, and the fixtures now match that.
- **Shipped in:** OTA, production channel, 2026-09-20, master @ `2f8195f`. Android group `10b5ab16-ef93-4585-b5f9-9a2f6c4bfae1` (runtime `c1907ba4…`); iOS group `7f5a5b0b-0e2a-4ebc-996f-0f7860426993` (runtime `5359dcce…`).
- **Verified:** Own device pass, reported by Robbie 2026-09-20: passed on **Pixel and iOS**. Cold start showed workouts without a pull-to-refresh, a foreground inside 15 minutes made no extra call, and data updated after 15. Not yet exercised by a tester, so this stays `Fixed`, not `Verified`.
- **Status:** Fixed

### PL-019 — Dropped WHOOP cycles are never closed or deleted

- **Severity:** Minor
- **Reported as:** Measured on production while checking which cycle maps to "today".
- **Root cause:** `supabase/functions/whoop-sync/index.ts` only ever upserts (blind upserts, `:290-297`); it has no delete or close path (`grep` for `.delete(`/`delete from` returns nothing). A cycle WHOOP later drops or re-scopes stays in `whoop_cycles` with `"end" IS NULL` forever, because the rolling 7-day window (`:492-504`) stops re-pulling it. Measured: u1 has **two** rows with `end IS NULL` — one open 0.8 days (genuine, current) and one open **57.7 days**, last written 81,741 minutes ago. Both surface as `is_current = true` in `biometric_periods_resolved`, so that user has 2 "current" frames.
- **Blast radius today:** contained. `whoop_cycle_nutrition`'s 36-hour guard gives a stale open cycle `effective_end = NULL`, so it owns no meals, and `prev_cycle_contiguous` is false for its successor. The orphan's wake-anchored `local_date` sits 57.7 days in the past, so a date-keyed read is unaffected.
- **Constraint going forward:** **nothing may select "today's cycle" via `is_current`** — including the LLM readiness query. `is_current` is not unique per user and is not a date. Select by wake-anchored `local_date` instead (`biometric_periods_resolved.local_date`).
- **Fix:** _not scheduled. Options: a reconciliation pass that closes or deletes cycles absent from a re-pulled window, or accept and rely on the date-keyed reads plus the constraint above._
- **Status:** Logged

### PL-023 — A failed goals read makes Settings persist the defaults over real targets

- **Severity:** Blocker (silent data loss — the user's own saved targets)
- **Reported as:** Found while answering a read-only challenge to the PL-017 fix: under RLS a query run without a valid session returns **zero rows, not an error**, so `maybeSingle()`'s no-row branch cannot tell "this user has no goals row" from "that read didn't carry a session". Chasing whether anything could then *write* the defaults back turned up a path that does.
- **Root cause — three parts, all of which already existed:**
  1. **The form seeds once and never re-syncs.** `SettingsScreen.tsx:129-138` builds `values` in a `useState` **initialiser** from the store's `goals`. `goals` is destructured from the store so the component re-renders when it changes, but `values` does not follow it — the only `setValues` in the file is `handleChange` (`:491`). There is no effect syncing the two.
  2. **Save sends all eight fields, not the changed one.** `handleSave` (`SettingsScreen.tsx:495-505`) passes a complete `Goals` object, each field falling back to the same literal defaults (`|| 2000`, `|| 150`, …).
  3. **The write is a full-row upsert.** `saveGoals` (`useStore.ts:1452-1471`) upserts all eight columns keyed on the `user_id` primary key. There is no partial update anywhere — this is the **only** write to `public.goals` in the codebase (`grep` for `from("goals")` returns exactly two sites: this and the read).
- **The sequence:** anything that leaves the store holding `DEFAULT_GOALS` while the user *does* have a real row → the user opens Settings and sees 2000 kcal instead of their targets → they correct one field and press Save → all eight are upserted → **their real targets are gone, with no error and no undo.**
- **How the store ends up holding the defaults — the common route needs no RLS subtlety at all:** any failed `fetchGoals` does it. A network failure at launch reports to Sentry and leaves `DEFAULT_GOALS` in place, and nothing retries or tells the user the screen they are about to edit is showing placeholder values.
- **The RLS route, measured:** `_getAccessToken` falls back to the **anon key** when `getSession()` yields null (`@supabase/supabase-js/src/SupabaseClient.ts:570-578`), and the token is resolved per request inside `fetchWithAuth` (`src/lib/fetch.ts:42-52`), so such a request reaches PostgREST as the `anon` role. Confirmed against production, read-only: `anon` holds **7 privileges** on `public.goals` (SELECT among them), and all three SELECT policies are `(auth.uid() = user_id)` with `polroles` **null** — i.e. `PUBLIC`, so they apply to `anon`. With `auth.uid()` NULL the qualifier is NULL, not true: **zero rows, HTTP 200, no error.** The read is silently empty rather than failing.
- **Not introduced by the PL-017 fix, but the fix widens the window.** Before it, `.single()` turned an empty read into PGRST116 and the handler's `if (data)` left the store alone — which preserved *already-loaded* goals. The new explicit `if (!data) set({ goals: DEFAULT_GOALS })` clobbers them. On the cold-start path the outcome is identical either way (state starts at `DEFAULT_GOALS`), so the write-back hazard is fully reachable on both sides of the fix; what changed is that it is now also reachable **after** a successful load. See PL-017.
- **Blast radius:** one row per affected user, overwritten in place. `goals` has no history, no `deleted_at` and no audit trail, so the previous values are unrecoverable from the database. Users who never set targets are unaffected — the defaults are already their state.
- **Fix — goals carry an explicit load state.** `goalsState: "loading" | "loaded" | "absent" | "error"` (`useStore.ts`), because `DEFAULT_GOALS` in `goals` is indistinguishable from a user whose targets happen to be the defaults, and every consumer — Settings most of all — was reading it as if it were the truth. `loaded` and `absent` are known good and may be written from; `loading` and `error` may not.
  - **Session gate on the read.** `fetchGoals` now calls `supabase.auth.getSession()` and returns `error` without querying when there is no session. This is what closes the anon-key hole: an empty result is only believable if the read actually carried the user's JWT. Not reported to Sentry — a missing session is a lifecycle state, not a fault.
  - **A failed read never downgrades a known-good state.** If `goalsState` is already `loaded` or `absent`, a failure keeps both the goals and the state. Only a failure with nothing known (cold start) gives `error` + `DEFAULT_GOALS`, and those defaults are explicitly display-only.
  - **`absent` is not an error (PL-017).** An empty read *with* a session sets `absent` + `DEFAULT_GOALS` and leaves a Sentry **breadcrumb**, not an event — `noteBreadcrumb()` in `src/lib/reportError.ts`, at `level: "info"` so it can't be misread as a failure. A later error now carries "goals: no row for user" in its trail.
  - **Writes are split by state.** `loaded` → `UPDATE` **only the columns that actually changed**, so a field the user never touched is never written, even from a stale form. `absent` → `INSERT` the full row, then `loaded`. Deliberately an insert and not an upsert: if a row does exist after all, the unique violation is the correct outcome rather than an overwrite. `loading`/`error` → refused with a message, no query.
  - **A zero-row UPDATE is a failure.** An `UPDATE` filtered out by RLS returns no PostgREST error — the `USING` clause just empties the target set and the request "succeeds". `.select("user_id")` plus a zero-length check, the same trap already handled in `saveCompositionApplyQuantities`.
  - **Settings re-syncs, and can't save what it doesn't know.** `values` follows `goals` in an effect instead of a once-only `useState` initialiser, guarded by a `dirty` flag so a late read never overwrites what someone is typing. Save is disabled unless the state is writable, and `handleSave` returns early too — a screen is a bad place for the only copy of a data-integrity rule. In `loading`/`error` the card shows "Couldn't load your targets" and a Retry, theme tokens only.
  - **Foreground retry.** `App.tsx`'s existing `AppState` → `active` listener re-runs `fetchGoals` **only while in `error`**, so the common case (no signal at launch, signal a minute later) fixes itself without the user finding Retry. `loaded` and `absent` are not re-read: that would be an unbounded query per foreground for data that cannot change from this device.
- **Behaviour deliberately unchanged:** a user with no row still runs on `DEFAULT_GOALS` (P-TF01b, still open), and Today's ring and History's adherence still render from `goals` whatever the state. Both are display-only (audited: `TodayScreen.tsx:717-718`, `:754-775`, `:911-1024`; `HistoryScreen.tsx:118-123`, `:240-241`) — no other consumer reads goals at all, `csv.ts` never touches them, and no lib module or Edge Function does either.
- **Where:** `<this commit>` — `src/store/useStore.ts` (`GoalsState`, `fetchGoals`, `saveGoals`, initial state, `reset`), `src/lib/reportError.ts` (`noteBreadcrumb`), `src/screens/SettingsScreen.tsx`, `App.tsx`, `vitest.setup.ts` (`auth.getSession` mock).
- **Tests:** `src/store/__tests__/useStore.test.ts` — 17 across `fetchGoals`/`saveGoals`, red first (15 of 17 failed; the two that passed were the pre-existing no-user exits, kept to pin them). Nine sabotage runs, each discriminating: removing the session gate (1), empty read → `error` (2), failure after a good load clobbering the store (2), dropping the write-state guard (2), writing all eight columns instead of the changed ones — the original bug — (2), treating a zero-row UPDATE as success (1), `absent` not promoting to `loaded` (1), `reset()` leaving the state (2), removing the breadcrumb (1).
- **A structural test caught something on the way.** `mealEntriesInsertSites.test.ts`'s "uninspectable update payloads is exactly {updateEntry}" went RED — not because of anything about `meal_entries`, but because its `resolvesToObjectLiteral` helper looks variable declarations up **by name across the whole file**. Naming a local `patch` inside `saveGoals` made `updateEntry`'s `{ ...patch }` (a spread of its *parameter*) resolve to my unrelated `{}` and appear traceable. Renaming mine to `changes` restored it. **The test is right to be loud, but it is weaker than it reads:** any future local named `patch` anywhere in `useStore.ts` silently converts that exemption into the "stale exemption, delete this test" branch, which is the opposite of what it intends. Worth a scope-aware resolver, logged here rather than fixed in this PR.
- **Sentry search for exposure — please run:** `operation:fetchGoals !error_code:PGRST116`. **Every one of those events is a launch where the store sat on `DEFAULT_GOALS` with no way to tell.** That is the best available measure of how many users could have been exposed to this, and the count, distinct users and first/last seen are all worth having. Note the two caveats from PL-017: this needs an **event-level** (Discover) query because the issue fingerprint is `[operation]` and groups all `fetchGoals` failures into one issue, and **distinct users will come back empty** until the per-install id ships (see the design decision above). ### PL-024 — Clearing a goal field silently saved the default

- **Severity:** Major
- **Reported as:** Flagged while building PL-023 as pre-existing and out of scope, then pulled into the same PR once it was clear PL-023 had made it worse.
- **Root cause:** `SettingsScreen.handleSave` parsed every field as `parseInt(values.x) || <default>`. That is three silent substitutions in one expression — a **cleared** field (`NaN`), a **typo** (`NaN`), and an explicit **0** (falsy) all became the hard-coded default — plus `parseInt`'s own truncation on top: `"150abc"` is `150`, and `"2,500"`, a perfectly reasonable way to type a calorie target, is **2**.
- **Why it got worse, not better, with PL-023.** While Save blind-upserted all eight columns from a form seeded at mount, a substituted default was one of eight values going over the row anyway. PL-023 writes **only the columns that changed** — and clearing a field *is* a change. So the substituted default became precisely and only what the write targets: the user clears their fibre goal, and 30 g is written to that one column as if they had chosen it.
- **Fix:** New pure module `src/lib/goalInput.ts`. `parseGoalField` refuses empty, whitespace, non-numeric, trailing junk, thousands separators and negatives, and returns a message per field instead of a value. `parseGoalValues` is all-or-nothing by construction: either a complete `Goals` or a map of per-field errors, with **no partial result**, because a partial result is exactly what a write path would be tempted to use. `handleSave` takes `parsedGoals.goals` or returns; nothing is substituted anywhere on the write path.
- **Which fields accept 0, and why:**
  - **All seven macros accept 0.** "No added sugar" and "as little salt as possible" are real targets, and `|| <default>` made them unreachable — typing 0 for sugar saved 30 g.
  - **Calories rejects 0**, with "Must be at least 1". A zero calorie goal isn't a target, it's a division by zero, and the codebase already agrees: both `TodayScreen`'s `frac()` (`goal > 0 ? … : 0`, `:91-92`) and `HistoryScreen`'s ring fraction (`:240`) special-case it.
- **Decimals follow the column type, measured rather than assumed.** Production `information_schema`: `calories`, `protein`, `carbs`, `fat` are `integer`; `sat_fat`, `salt`, `fibre`, `sugar` are `numeric` with no declared scale. So the first four reject a decimal ("Whole numbers only") rather than letting Postgres round `150.5` on the way in and hand back a number the user never chose; the other four accept one. Note this contradicts `schema.legacy-v2.LEGACY-DO-NOT-USE..sql`, which declares `salt numeric(4,1)` and `fibre`/`sugar` as `integer` — another reason not to read that file as current.
- **UI:** each row shows its own message under the input and turns the input border `Colors.danger`; Save is disabled unless the store is writable **and** every field parses (`canSaveGoals = goalsWritable && goalsValid`). Theme tokens only.
- **Where:** `<this commit>` — `src/lib/goalInput.ts` (new), `src/screens/SettingsScreen.tsx`
- **Tests:** `src/lib/__tests__/goalInput.test.ts` (16, red first — the module didn't exist) plus the write-gate assertions in `src/screens/__tests__/settingsGoalsCopy.test.ts`. Sabotage runs: substituting a default on empty fails 4; loosening the parse to `parseFloat` fails 2 (`"150abc"`, `"2,500"`); restoring falsy-zero fails 2; allowing decimals on integer columns fails 1; restoring `parseInt || <default>` in `handleSave` fails 2; gating Save on `goalsWritable` alone fails 1. **One test caught itself**: the "no parseInt-or-default anywhere" assertion first failed against my own comment *describing* the bug, so it now matches comment-stripped source — a test that passes by forgetting why it exists is worth nothing.
- **Shipped in:** OTA, production channel, 2026-09-20, master @ `5f347c3`. Android group `faa10722-93cb-4cc2-878b-b5bbcde64c15` (runtime `c1907ba4…`); iOS group `75060c2b-bc04-46b8-8453-2813afe53a52` (runtime `5359dcce…`).
- **Verified:** Own device pass, reported by Robbie 2026-09-20: **passed on Pixel**. Clearing a target disabled Save with an inline error, an explicit 0 saved as 0, and the rejected shapes behaved — `"2,500"`, `"150abc"` and a decimal on an integer column each refused rather than silently writing a number. **iOS not run this round — owed.** Not yet exercised by a tester, so this stays `Fixed`.

## Constraint — WHOOP ids are unique PER USER; every join needs `user_id`

Filed alongside PL-009's "don't compare the small four as text in SQL", PL-019's "never select today's cycle via `is_current`", and the `source_updated_at` constraint below.

`whoop_cycles`' primary key is **`(user_id, id)`**, not `id`. The same WHOOP cycle id can belong to two different users, and on production it does: id `1806788975` is held by both `4dbf04ae…` and `a8435663…`. The same applies to the other `whoop_*` tables, which are keyed the same way.

**So every join between `whoop_*` tables, and every ad-hoc query against them, must include `user_id`.** A join on `id` alone does not fail — it silently produces a cross product between users, which is worse than an error because the result still looks like data.

- **RLS protects the app.** Each table is filtered to the signed-in user *before* any join, so a client read cannot mix users.
- **Service-role and SQL-editor queries are not protected**, and that is where this bites. It is also where verification SQL runs, which is how a wrong join gets to invalidate the evidence for a change rather than the change itself.
- **All four views were audited on 2026-09-20 and every one of their joins already includes `user_id`** — `biometric_periods` (2 joins), `biometric_periods_resolved` (12), `whoop_correlation` (3), `whoop_cycle_nutrition` (1). Eighteen joins, all correct. No issue logged: nothing shipped is wrong.

**How it was found, which is the part worth keeping.** PR 6's own justification was measured with a join on `id` alone. It reported "2 of 172 rows diverge by up to 17.6 hours" when the truth is 116 rows and zero divergence. The dry run caught it because one of the two fabricated drifts was **negative**, and `GREATEST(c, r, s)` can never be less than `c` — an impossible number, not a suspicious one. A plausible wrong number would have survived.

## Constraint — `source_updated_at` is a whole-FRAME signal, never strain's time

Filed alongside PL-009's "don't compare the small four as text in SQL" and PL-019's "never select today's cycle via `is_current`", because it is the same kind of trap: a column whose name suggests one thing and whose definition says another.

`biometric_periods` defines it as `greatest(c.whoop_updated_at, r.whoop_updated_at, s.whoop_updated_at)` — cycle, recovery **and** sleep — described in the migration itself as a "freshness signal across all three joined sources". `biometric_periods_resolved` passes it through unchanged.

**So it answers "when did this WHOOP frame last change?", not "when was this number calculated?"** It is a whole-frame signal **by definition**, whatever the data happens to look like. Presenting it under strain would show the sleep scoring time whenever sleep was scored later than the cycle — which does not happen on current data, and which nothing prevents.

**Measured on production: 116 WHOOP rows, ZERO divergence** — `source_updated_at` equals the cycle's own `whoop_updated_at` on every row, and across all 116 cycles neither recovery nor sleep is ever newer than its cycle. So the two coincide on all current data.

**An earlier version of this record claimed 2 of 172 rows (1.2%), up to 17.6 hours. That figure was wrong and is withdrawn.** It came from joining `whoop_cycles` on `id` alone. The primary key is `(user_id, id)` — WHOOP cycle ids are unique PER USER, and two users genuinely share id `1806788975` — so the join cross-multiplied them, inflating 116 rows to 172 and manufacturing a symmetric ±1,053.5-minute "drift" out of one user's frame timestamp against another user's cycle. **PR 6's dry run caught it**, because one of the two drifts was NEGATIVE and `GREATEST(c, r, s)` can never be less than `c`. The impossible number was the tell.

- **Never attach it to a single metric** — not strain, not recovery, not sleep. It belongs to the row.
- **The readiness query must not use it as a per-metric recency or staleness input.** A "your strain data is N hours old" derived from it is correct only for as long as WHOOP keeps bumping the cycle whenever it rescores recovery or sleep. Nothing enforces that, and the failure would be silent. Use `strain_updated_at` (PR 6).
- Per-metric timestamps need their own columns. PR 6 adds `strain_updated_at`.
- The Health Connect arm of the resolved view selects `null::timestamptz` for it, so it is absent for HC-sourced periods entirely.

## PR 4 — WHOOP connection state and `getWhoopScoresForDate` (no UI)

Not a defect. A feature slice, recorded here because two decisions and one measured caveat came out of it that the next round needs.

**Shipped in:** OTA, production channel, 2026-09-20, master @ `3fb3373`. Android group `7c0b4336-d65c-409d-a7b9-29f15188be27` (runtime `c1907ba4…`); iOS group `6f4454b1-5773-4270-b80f-f36fa7b974e8` (runtime `5359dcce…`). Committed at `dcf43f0`; shipped together with PR 5, which is the first thing to render any of it.

### The cold-start layout decision

Today's WHOOP panel sits in an 82dp column beside the calorie ring, so "is WHOOP connected?" decides the **layout**, not just the content. The connection row cannot be read before the Supabase session is restored — `getSession()` awaits `initializePromise`, and supabase-js resolves the access token per request — so a cold start that waits for the network renders the centred, no-column layout and then jumps the ring sideways when the row lands. Every launch, for exactly the users the feature is for.

**Measured:** the `whoop_connections` round trip is **35 ms min / 42 ms median / 76 ms p90 / 89 ms max**, from the dev machine on a wired connection, 10 samples after 2 warm-ups. That is a **floor, not the answer** — it is not a Pixel on mobile data, and the query cannot start until the session is restored, so the real delay is `AsyncStorage read + auth init + one round trip`. The first two were not measured; doing so needs a build and a timed log on the device.

**Decision (Robbie, 2026-09-20):** seed the connection state from a local AsyncStorage cache, then reconcile. The stale-revoked case — a user who revoked on WHOOP's site since the last launch sees the panel with "–" for one round trip — is **accepted**.

Conditions, all built: the cache holds `{ userId, connected }` and nothing else (no tokens, no scores, no connection-row fields); a cache whose `userId` doesn't match the restored session counts as missing; `reset()` removes it; a failed reconcile **keeps** the cached state and reports once (PL-014), so only a *successful* read moves the layout; Settings' connect and disconnect write the store and the cache in one action.

`@react-native-async-storage/async-storage` was already a direct dependency at `2.2.0`, so `package.json` is unchanged and there was no fingerprint question to answer.

### The strain caption — decision, and a measured caveat

**Decision (Robbie, 2026-09-20): `asOf` is `source_updated_at` — WHOOP's own last calculation, not our pull time.** For a score, WHOOP's calculation time is the honest "as of"; when plated last pulled the row says nothing about the number's freshness. **This supersedes the earlier "strain shows last-synced time" default**, and `whoop_connections.last_sync_at` is not used for this at all. Everything in the code and tests that said `synced` has been renamed to match what the value is.

**Caveat, measured, and it is not what the column name suggests.** `biometric_periods` defines it as:

```sql
greatest(c.whoop_updated_at, r.whoop_updated_at, s.whoop_updated_at) as source_updated_at
```

— cycle, recovery **and** sleep, described in the migration as "freshness signal across all three joined sources". `biometric_periods_resolved` passes it through unchanged. So it is **"when this WHOOP frame last changed"**, not "when strain was calculated", and a sleep or recovery record updated later than the cycle carries the caption with it.

**Withdrawn measurement.** This record originally claimed 2 of 172 rows (1.2%), up to 17.6 hours. That was a join artifact — see the corrected figure in the `source_updated_at` constraint above. The real number is **116 rows, zero divergence**. The concern is structural, not observed: nothing enforces `GREATEST(c, r, s) = c`.

Separately: the Health Connect arm of the resolved view selects `null::timestamptz` for this column, so an HC-sourced period has no caption at all. That falls out correctly — `asOf` null means no caption — but it means the caption is a WHOOP-only affordance.

**Connection: 15 tests, 8 sabotage runs. Scores: 25 tests, 8 sabotage runs.** 731 total green, `tsc` clean.

**These were written AFTER the implementation, not red-first.** Both suites. ## Design decision — a per-install analytics id for Sentry, scheduled after the WHOOP panel

Not a defect and not a PL- issue — a decision taken 2026-09-20, recorded so it isn't re-argued.

**The problem it solves.** Sentry currently cannot tell "1 user hit this 400 times" from "400 users hit it once". `instrument.ts` sets `sendDefaultPii: false` and `beforeSend` does `event.user = undefined` ("we never attach a user; hard-clear in case anything populates it"), and nothing in the app calls `Sentry.setUser`. So every issue's "users affected" is empty. That surfaced while scoping the PL-003 and PL-017 Sentry queries, both of which ask for distinct users and cannot get it.

**Decision: yes, but a random UUID, not a hash of the Supabase user id.** Hashing the user id is only *pseudonymisation* — we hold the id set, so the mapping is reversible by enumerating our own users against the hash. A UUID generated on first launch and stored locally is a genuinely weaker identifier: it carries no relationship to the account, it does not survive a reinstall, and it does exactly the one job needed, which is separating one noisy install from many quiet ones.

**It is still an online identifier under UK GDPR**, so it needs a line in the privacy policy (`https://platedapp.uk/plated-privacy.html`, linked from `AboutScreen.tsx:20`) before it ships. That is part of the work, not a follow-up to it.

**Scheduled after the WHOOP scores panel (PR 4 / PR 5).** It changes nothing retrospectively — a fresh id can only attribute events from the build that introduces it, so shipping it sooner does not improve the PL-003 or PL-017 counts currently owed. Those stay uncounted-by-user whichever order this lands in.

**Notes for whoever builds it:** it will need the `event.user = undefined` line in `beforeSend` narrowed rather than removed (the point of that line is that the *Supabase* user never reaches Sentry — that must stay true); `@react-native-async-storage/async-storage` is already a dependency and is the natural home for the id; and it must be generated, never derived from any account, device or install identifier.

### PL-028 — A product with no nutrition data in Open Food Facts is stored as all-zero, and a bundle freezes that forever

- **Severity:** Major
- **Reported as:** Robbie, 2026-09-20: "Chia Seeds (AKSOY, 10 g) was logged at 43 kcal / 2.2 P / 0.7 C / 2.9 F up to 2026-09-08. From 2026-09-14 it's 0 for every nutrient."
- **Status:** Logged — investigated read-only, no fix proposed yet, as asked.

**The reported timeline is the wrong way round, and that matters.** Pulling every row for barcode `5060731352170` (54 entries, 15 Jul → 20 Sep) shows the zeros are the **default state of this product, not a September regression**:

| Dates | Source | Values |
|---|---|---|
| 15 Jul | `barcode` (the original scan) | **all zero** |
| 16 Jul – 14 Aug | `bundle`, `copied` | **all zero** |
| 16 Aug – 7 Sep | `custom`, then `copied` | 42.70 / 2.19 / 0.69 / 2.86 |
| 1 Sep, 18 Sep | `custom` | 43.70 / 2.21 / 2.38 / 1.90 |
| 14 Sep | `bundle` | **all zero** |
| 15 – 20 Sep | `copied` | **all zero** |

So the **correct values were the exception** — they came from a custom food created by hand on 16 Aug, not from the product. The 14 Sep row didn't break anything; it restored the original state.

**Root cause — confirmed at every step, in order.**

1. **Open Food Facts has no nutrition data for this product.** Queried live: barcode `5060731352170` returns `status: 1` with `product_name: "Chia Seeds"`, `brands: "AKSOY"`, and **0 of 8 nutriment fields present** — not zeros, *absent keys*. Same for `20699321` ("Brown onions"), 0 of 8. This is PL-012's "check the OFF source first" answered: the app is not mis-parsing or mis-scaling anything, and there is no per-100g bug. OFF genuinely knows nothing.
2. **`parseProduct` coalesces the big four to 0.** `src/lib/openfoodfacts.ts:254` (`cal = cal ?? 0`) and `:313-316` (`(n["proteins_100g"] ?? 0)`, same for carbs and fat). The **small four are handled correctly** and stay `undefined` — which is why the Brown onions items carry NULL sat fat/salt/fibre/sugar beside a zeroed big four. The file says why, at `:301-305`: "OFF itself sometimes reports those as a genuine (if low-quality) 0, which the adapter must pass through faithfully."
   **That reasoning conflates two different facts.** "OFF reports 0" and "OFF has no key at all" both become `0`, and only the second is a lie. They are trivially distinguishable — this product has *zero* nutriment keys — without touching the NOT NULL columns or `FoodProduct`'s non-optional `cal_per100`.
3. **A bundle freezes the snapshot, correctly, and that is what made it permanent.** Two bundles contain this item: **"Ultimate Yogurt Breakfast"** (created 15 Jul) holds it **all-zero**, and **"New Breaky"** (created 29 Aug, after the user's manual correction) holds it at 42.7 / 2.19 / 0.69 / 2.86 with `salt` correctly **NULL**. Applying the old bundle on 14 Sep wrote the July snapshot back, and copy-forward propagated it for six days. **The apply path and the bundle design are both working as intended** — freezing values is the point of a bundle. The defect is entirely in what was frozen.

**Blast radius — smaller than the raw count, and two of the five "defects" aren't defects.**

Five bundle items across 4 bundles and 2 users have an all-zero big four, out of 46 items in 9 bundles. But:

| Item | Bundle | Verdict |
|---|---|---|
| Chia Seeds, 10 g | Ultimate Yogurt Breakfast | **Wrong** — chia is ~486 kcal/100 g |
| Brown onions, 150 g | Bolognese | **Wrong** — onions are ~40 kcal/100 g |
| Brown onions, 100 g | Salt pepper chips and chicken | **Wrong** |
| Salt, 6 g ×2 | Three bean chilli and avocado salsa | **Correct.** Table salt genuinely has 0 kcal / protein / carbs / fat, and these carry `salt = 5.895 g`, which is right for 6 g. A true zero, not a coerced one. |

So **3 real items, 2 users**. In `meal_entries`: **32 zeroed rows for the chia barcode across 2 users** (1 `barcode`, 10 `bundle`, 21 `copied`), spanning 15 Jul – 20 Sep. The second user has them via friend-copy. **Brown onions have produced no entries at all yet** — those two are **latent**, sitting in bundles waiting to be applied.

**Recoverability — different answers per item, and neither is a measurement.**

- **Chia Seeds: recoverable in principle.** The same barcode at the same 10 g serving has a known-good sibling — the "New Breaky" bundle item, plus ~20 correct `meal_entries` from 16 Aug – 7 Sep — all at 42.70 / 2.19 / 0.69 / 2.86. The 32 zeroed rows could be repaired from the user's own later correction.
- **Brown onions: not recoverable from anything we hold.** OFF has nothing, there is no custom food, and no non-zero row exists for that barcode anywhere in the database.
- **Both repairs would be inference, not measurement**, which is the same wall PL-002 and PL-012 hit: a stored 0 cannot be told apart from a real zero, and the two Salt rows above are precisely why a blanket "all-zero big four → repair" sweep would be wrong. Any repair has to be per-item and evidenced.

**Relationship to existing issues.** This is **PL-011** ("`meal_entries` big four can't represent unknown", Deferred) with a measured cost attached, and the mirror of **PL-002** (which fixed exactly this coercion for the small four in `saved_ingredients`). **PL-012** ("Tesco Gold Coffee library row saved all-zero — check the OFF source first") is almost certainly the same defect; that check is now done and the answer is "OFF had no data". Worth re-reading PL-012 against this.

**Not yet proposed:** a fix. Three directions exist — discriminate "no nutriment keys at all" from "OFF says 0" at the adapter; let the user see and correct an incoming zero before it is stored; and decide separately what, if anything, to do about the 32 existing rows. That is a decision, not an implementation detail, so it waits.
