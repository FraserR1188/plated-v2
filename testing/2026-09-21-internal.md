## Rectification log

### PL-034 — the y-axis labels render outside the card

- **Severity:** Minor. The chart is still readable and the number that matters most is not lost: the goal is written in the same card's header, in full, by `goalCaption`. What is wrong is the axis, and only at its left edge.
- **Reported as:** Observed on the Pixel. "2,800 renders as ',800', and 160/339 start outside the card border."
- **Root cause:** The y labels were RN `<Text>` with `position: "absolute"` and `right: 0`, inside a `yAxis` `<View>` given **no width at all** — deliberately, so that "the layout engine sizes it to its widest label" (the previous fix, `1d6babb`). It cannot. An absolutely positioned child does not contribute to its parent's content-based size, so the column measured **zero** wide, and every label was laid out at its natural width with its right edge on the column's right edge — which is also its left edge. Every label hung entirely into the space to its left, and was clipped by whatever ancestor happened to clip.

  The arithmetic matches all three reported symptoms, including the one that does *not* happen. The card's content edge sits 16 (scroll padding) + 1 (border) + 8 (card padding) = **25dp** from the screen edge, and JetBrains Mono's advance is 0.6 em, so at 9px each character is 5.4dp:

  | Label | Width | Left edge | Result |
  |---|---|---|---|
  | `2,800` | 27.0 | **−2.0** | past the screen edge; leading glyph cut → ",800" |
  | `339` / `160` | 16.2 | 8.8 | on screen, but 8dp outside the card's border at 17 |
  | `0` | 5.4 | 19.6 | inside the card — and it was not reported as wrong |

- **Why the previous fix looked right:** it replaced a *fixed* 26px gutter, which had clipped the same label the same way. Going from "a guess" to "let the layout engine measure it" is the correct instinct, and the commit message, the code comment and the device-pass record all describe it as done. The device pass that signed it off (`testing/2026-09-20-internal.md`, "Chart re-check — PASSED") lists "the top number reads in full — '2,800', not ',800'" as a check that passed. It did not.
- **And the test made it permanent.** `trendsUi.test.ts:176-182` asserted that the `yAxis` style block contains no `width:` — that is, it asserted *the very property that causes the bug*. A source-text test cannot tell "no width, because the engine will size it" from "no width, and it measures zero". It is the fifth structural blind spot in this feature, and the first where the test actively defended the defect.

- **Fix:** all of the chart's geometry and text moved into one pure function, `buildChartLayout` in `src/lib/trends.ts`. It returns the scale, the y ticks (value, label, y, baseline, whether to draw a gridline), the x labels (index, text, x), the gutter, the goal's y and whether there is any data at all. `TrendChart.tsx` maps those arrays onto svg elements and computes nothing — `Math.max`, `Math.min`, `buildChartScale`, `niceTicks`, `POINT_EXTENT` and `scaleTop` are all banned in it by test.

  - **The gutter** is `widest tick label × charW + 4`, so it is arithmetic rather than a hope about Yoga. The labels are svg `<Text>`, `textAnchor="end"`, inside it.
  - **Nice numbers.** `niceTicks(max)`: the step is the smallest of {1, 2, 2.5, 5} × 10^k at or above `max / 4`; the top is the first multiple of the step **strictly** above the max; ticks run 0 → top. Carbs now reads 0/100/200/300/400 instead of topping out at 339, and Calories 0/1,000/2,000/3,000 instead of at whichever of the goal or the best day was higher. Labels carry the step's own precision ("0.0, 0.1", "2.5, 5.0", "0, 100"), thousands separators, and no unit — the unit is in the header.
  - **Tick values are rounded to the step's precision.** 3 × 0.1 is 0.30000000000000004, which still *formats* as "0.3" but is not equal to a goal of 0.3.
  - **Gridlines** at every tick in the card's own border colour, under the goal line, which keeps its dashes. Where the goal sits exactly on a tick, that gridline is dropped and the label kept: two lines at one y is just a thicker line, and the dashes stop reading.
  - **X labels** all anchored "middle" on their own points; the plot is inset at both ends by half the widest label, which is what lets the end labels sit on their points rather than beside them. 7 days: "Mon 14" … "Sat 19", then **"Today"**. 14 days: every other day counting back from the last (13, 11, … 1), day-of-month only, with the month on the first label and again wherever it changes ("1 Oct"), and "Today" at the end.
  - **`CHART_HEIGHT` 108 → 150.** `X_LABEL_HEIGHT` stays 14, so all 42px went to the plot.

- **The font metrics are measured, not assumed.** Read out of the bundled `JetBrainsMono_400Regular.ttf` with fontTools: `unitsPerEm` 1000, advance width **600 for every glyph the labels use** (digits, comma, full stop, space, and the weekday/month letters), OS/2 `sCapHeight` **730** (cross-checked against the 'H' glyph bbox: 730), hhea descent −300. So the 0.6 em the old code assumed was right, and is now recorded as measured. At 9px: charW 5.4, cap height 6.57. Digits reach 740 — round shapes overshoot the cap line — which is 0.09px at 9px and not modelled.

- **One thing the old comments had backwards.** `TrendChart.tsx` said `includeFontPadding: false` made the y labels ignore the system font scale. It does not — it only drops Android's extra ascent/descent. RN `<Text>` scales with the OS font setting unless `allowFontScaling={false}`, which was never set anywhere in `src/`. So the old labels grew with the font scale while the geometry positioning them (`scale.plotTop − AXIS_FONT / 2`) did not, which would have pulled them further off their own lines at large type — a second, latent defect in the same component. Moot now: **svg text genuinely does not follow the font scale**, so the whole axis is fixed at 9px and the measured metrics hold at every Dynamic Type setting.

- **Where:** branch `feat/trends-axes`, off master @ `f47615d`. Red tests `e4d3ca4`; fix in the commit that follows it.
- **Shipped in:** _not yet — no OTA published from this round._ Fingerprints measured before the device pass: Android `c1907ba4619df4d22e128f15df609529906eae2a`, iOS `5359dccea82b8462c0d3d81501d9748bbb241baf` — **identical to the runtime versions the last OTA went out on**, and 0 of the 158 (Android) / 142 (iOS) fingerprint sources are files this change touches. No `src/` file is a fingerprint source at all, so this is OTA-eligible.

**Why the red count was predictable.** `vite-node` leaves a missing named export as `undefined` rather than throwing at link time, so `trends.test.ts` still *collects* when it imports functions that do not exist yet — the new tests fail individually on "not a function" while the 66 existing ones keep passing. That is a better red than a file-level collection error, which would have hidden whether the old tests still held.

### The sabotage runs

| # | Sabotage | Caught by |
|---|---|---|
| 1 | `top` at-or-above the max instead of strictly above | `niceTicks holds as a property` (the exact-nice maxima: 1, 2.5, 5, 10, 100, 200, 1000, 10000 — `top > max` fails) and `labels to the step's own precision` |
| 2 | Drop the float-noise rounding from the tick values | `uses tenths for a very small series, with no float noise` — **only that one** |
| 3 | Gutter computed from `charW / 2` | All 7 widths of `keeps every y label's ink inside [0, gutter]`, plus `widens the gutter for a wider label` |
| 4 | X inset back to `POINT_EXTENT` with the labels still centred | All 7 widths of `keeps every x label inside a plot, clear of the gutter` |
| 5 | Keep the gridline where the goal equals a tick | `drops the gridline where the goal sits exactly on a tick` and `matches a goal that is a tick even through float noise` |
| 6 | Recompute the scale max inside `TrendChart.tsx` | `delegates the whole layout to the tested builder` (the `Math.max` ban) and `draws the y labels as svg text inside the computed gutter` |

**Sabotage 2 is the interesting one.** Only the direct tick-equality assertion caught it; the gridline dedupe did not, because that comparison carries a `step × 1e-6` tolerance which absorbs a 5.5e-17 error. That is the tolerance doing its job, but it means the rounding's real justification is narrower than "the dedupe needs it": it is that a tick value should *be* the number it prints as, for every consumer downstream, including ones that have not been written yet.

**A process note.** The first sabotage harness shelled out to `git checkout --` to revert, and crashed on a Unicode decode error before reaching it — with the implementation still uncommitted, so three sabotages stacked up in the working tree and a `git checkout` would have destroyed the fix rather than the sabotage. Repaired by hand, re-verified green, and the harness rewritten to restore the file's original bytes from memory in a `finally`. **Never revert an experiment with git while the thing being experimented on is uncommitted.**
