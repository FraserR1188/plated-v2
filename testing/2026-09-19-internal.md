### PL-007 — CSV and last30Days use UTC dates

- **Severity:** Major
- **Root cause:** `csv.ts` uses `toISOString().slice(0,10)` next to a local-time column, so a meal at 00:30 BST exports under the previous day. `last30Days` computes its range in UTC too. Both break the dateKey invariant.
- **Sweep of `src/` for other UTC date-keying — nothing else to fix.** Every `toISOString()` call in `src/` was checked and classified. The only date-KEYING uses (an ISO string sliced to a calendar day) were the three in `csv.ts`. Everything else passes a **full ISO timestamp** to a `timestamptz` column or a formatter, which is correct and must stay: `batchLogMessage.ts:32` (pairs it with `dateKey(chosenAt)` for the day, already right), `compositions.ts:900` (`eaten_at`), `entries.ts:78`, `healthConnectSync.ts:393-394,417-418,454-455,527,570` (sync window bounds, genuinely absolute instants), `social.ts:742-743`, `time.ts:152`, `BatchesScreen.tsx:265,337,354`, `ProductScreen.tsx:438,668,1119,1136`, `TodayScreen.tsx:1826`, `useStore.ts:801,924,993,1025,1208,1412,1551,1571`. Separate greps for `split("T")[0]`, `getUTCDate`/`getUTCMonth`/`getUTCFullYear`, `substring(0,10)` and `substr(0,10)` returned only the two comments that warn against the pattern (`entries.ts:406`, `time.ts:44`). **No new PL- issues from the sweep.**
- **Fix:** `buildCsv` (split out of `exportCSV` so the rules can be tested without a filesystem or a share sheet) uses `dateKey(eaten)` for the date column. `last30Days` builds its bounds from local calendar fields.
  - **The export filename was wrong the same way** (`plated_${new Date().toISOString().slice(0,10)}.csv`) — a file exported at 00:30 BST was named for yesterday. Fixed in the same pass; it is in `csv.ts` and is the same defect.
  - **`last30Days` had a second bug the UTC one was hiding: fixed-millisecond arithmetic.** `Date.now() - 30 * 864e5` is not calendar arithmetic. Crossing a DST transition shifts the wall clock by an hour, which moves the start date by a whole day when the export happens within an hour of midnight — in one direction the window silently becomes 31 days, in the other 29. It now steps back with `setDate()` on local calendar fields, which has no such edge.
  - **Behaviour change, deliberate and worth stating: the window is now exactly 30 local days, where it was 31.** The old range ran `now - 30` to `now` **inclusive**, so a function called `last30Days` returned 31 days of data. It is now `now - 29` to `now` inclusive. Anyone diffing an old export against a new one will find one fewer day at the start, in addition to the corrected dates.
- **Where:** `<this commit>` — `src/lib/csv.ts`, `vitest.setup.ts` (timezone pin + expo mocks)
- **Callers of `last30Days`, and what changes for each:** exactly one — `SettingsScreen.tsx:565`, `last30Days(getAllEntries())` feeding `exportCSV` from the Export button. For it: the export covers 30 local days rather than 31 UTC-bounded ones; an export run between midnight and 01:00 BST no longer silently omits everything already logged "today"; and the window no longer changes length around a DST transition. The new optional `now` parameter defaults to `new Date()`, so the call site is unchanged. `filterByDateRange` has no other caller.
- **The test suite is now pinned to `Europe/London` (`vitest.setup.ts`).** This is load-bearing, not tidying: under UTC `dateKey()` and `toISOString().slice(0,10)` agree *exactly*, so a test written to catch this class of bug is vacuous there. The dev machine is Europe/London and CI's ubuntu runner is UTC, which is the worst arrangement — green locally, green in CI, regression ships. Measured both ways: with the pin removed, three of the date assertions fail loudly in UTC (they encode London semantics) and the `dateKey`-equivalence test goes **vacuous**, passing against the broken code. The pin makes the suite both meaningful and green on any machine.
- **Tests:** `src/lib/__tests__/csv.test.ts` (14, red first — 13 failed before the fix, the 14th is a DST case added afterwards). Sabotage runs: reintroducing `toISOString` for the date column fails 4; UTC bounds in `last30Days` fails 4; a 31-day window fails 4; fixed-millisecond arithmetic with local keys fails 2.
- **A sabotage run caught a vacuous test of mine.** The first BST→GMT fixture used local **noon** on both sides of the change, and the fixed-millisecond sabotage PASSED it: crossing a transition moves the wall clock by an hour, which only changes the calendar *day* when the time of day is within an hour of midnight. At noon the bug is invisible. Replaced with two fixtures at **opposite ends of the local day** — 23:30 across BST→GMT (the window shrinks to 29) and 00:30 across GMT→BST (it grows to 31) — because the arithmetic is wrong in both directions and one fixture can only ever show one of them.
- **Shipped in:** _not yet published._
- **Verified:** Own device pass, reported by Robbie 2026-09-20: **passed on Pixel**. A 00:30 entry exported as **2026-09-20**, its own local day, and the filename was right. The window came out **22 Aug – 20 Sep** — 30 local days inclusive, exactly as intended — with 25 and 27 Aug inside and 16 and 19 Aug outside it. The file opened cleanly in Sheets/Excel. **iOS not run — owed to the next tester session.** Not yet exercised by a tester, so this stays `Fixed`.
- **Status:** Fixed

### PL-008 — CSV exports NULL as 0.0

- **Severity:** Major
- **Root cause:** `csv.ts` formats the small four with `toFixed` and no NULL branch, which breaks NULL-not-zero outside the database.
- **Why it matters beyond the cell:** a stored NULL means "we never knew this". `(e.sat_fat ?? 0).toFixed(1)` asserts the food contained none of it — the same fabrication PL-002 fixed in `saved_ingredients`, arriving at the user's analysis by a different route, and worse here because a spreadsheet has no way to tell an invented zero from a measured one. An empty cell is read as missing by Excel, Sheets, R and pandas alike, and `AVERAGE()` skips it instead of dragging the mean down.
- **Fix:** One `optionalCell(v, places)` helper: `v == null ? "" : v.toFixed(places)`. Applied to all four (`sat_fat` 1dp, `salt` 2dp, `fibre` 1dp, `sugar` 1dp — decimal places unchanged). `== null` rather than `=== null` so an absent key behaves like an explicit NULL. `serving_g` already did exactly this two lines above, so the file now treats every nullable column the same way. The big four need no branch: `calories`/`protein`/`carbs`/`fat` are non-nullable in `MealEntry`, which is PL-011 and stays open.
- **Header row and column order unchanged**, pinned by a test against the literal `CSV_HEADER` string — an existing spreadsheet keyed on these columns should not break because the values underneath got fixed.
- **Where:** `<this commit>` — `src/lib/csv.ts`
- **Tests:** in `src/lib/__tests__/csv.test.ts` above — NULL exports empty, an explicit 0 exports as `0.0`/`0.00`, `undefined` behaves like NULL, and real values keep their decimal places. Sabotage: restoring `(v ?? 0).toFixed(places)` fails 2.
- **Shipped in:** _not yet published._
- **Verified:** Own device pass, reported by Robbie 2026-09-20: **passed on Pixel**. A row with a known NULL small four (Vimto gel, 2026-09-05) exported as **empty cells**, and a real 0 exported as **0.0** — the two cases the fix exists to separate, distinguished in the actual file rather than in a test. Opened cleanly in Sheets/Excel. **iOS not run — owed to the next tester session.** Not yet exercised by a tester, so this stays `Fixed`.
- **Status:** Fixed

### PL-017 — Users without targets report fetchGoals errors to Sentry

- **Severity:** Minor
- **Reported as:** Predicted from the code while recording P-TF01b. Not checked in Sentry.
- **Root cause:** Sign-up (`handle_new_user`, `20260819101000_profile_on_signup.sql`) creates a `profiles` row but no `goals` row. `fetchGoals` (`useStore.ts:639-661`) reads with `.single()`, and PostgREST answers "no row" with an error (code `PGRST116`, HTTP 406). That error is reported at level `error` (`useStore.ts:647`). `fetchGoals` runs on every auth event that has a session (`App.tsx:123`: cold launch, sign-in, token refresh), so each of those sends one report until the user saves targets in Settings. The app itself carries on with `DEFAULT_GOALS`.
- **Sentry search:** `operation:fetchGoals` (issue fingerprint `fetchGoals`). The no-row case should also carry `error_code:PGRST116`. Only builds with `__DEV__` off report (preview and production). **Not yet run** — no Sentry credentials are reachable from the dev machine (no `SENTRY_AUTH_TOKEN`, no `.sentryclirc`, no Sentry MCP), so the count, distinct users and first/last seen are still owed. Two notes for whoever runs it: the default fingerprint is `[operation]`, so every `fetchGoals` failure groups into ONE issue regardless of code — filtering the *issue* list by `error_code:PGRST116` shows that issue's total, not the PGRST116 subset, so the count has to come from an event-level (Discover) query. And **distinct users will come back empty whatever the query**: `instrument.ts` sets `sendDefaultPii: false` and `beforeSend` does `event.user = undefined`, and nothing calls `Sentry.setUser`. See the per-install identifier decision in `testing/2026-09-20-internal.md`.
- **Fixed without waiting for the numbers.** The source is unambiguous on its own: `.single()` on a table with no row for that user returns PGRST116, and the handler reported every error at level `error`. The Sentry numbers would have told us how many users, not whether the path exists — and leaving it in place was polluting the `operation:fetchGoals` signal the PL-003/PL-017 queries are about to rely on.
- **Fix:** `fetchGoals` reads with `.maybeSingle()`, which answers zero rows with `{ data: null, error: null }`, and the handler now has three explicit branches instead of two: a genuine `error` is reported and the loaded goals are kept; `!data` sets `DEFAULT_GOALS`; a real row maps as before. No `PGRST116` code check was added alongside it — with `maybeSingle` this query can no longer produce that code, so a check for it would be dead code that swallows a real error if the query shape ever changes. The `satFat` fallback now reads `DEFAULT_GOALS.satFat` rather than a duplicated literal `20`.
- **Behaviour is unchanged for the user.** A user with no targets still runs on `DEFAULT_GOALS` (2000 kcal) — that is P-TF01b, which stays open. The no-row branch is *explicit* rather than a fall-through, so a row deleted under a signed-in user now drops back to the defaults instead of leaving stale targets on screen; previously that case took the error path and kept them.
- **Where:** `<this commit>` — `src/store/useStore.ts:639-687`
- **Tests:** `src/store/__tests__/useStore.test.ts` (7 new, red first — 6 of the 7 failed against `.single()`; the 7th, the no-user early return, passed before and after and is there to pin it). The mock deliberately exposes only `.maybeSingle()`, so a regression to `.single()` fails loudly rather than quietly. Sabotage runs: reverting to `.single()` fails 6; reporting the no-row case anyway (the bug, reproduced behaviourally while keeping `maybeSingle`) fails exactly the "nothing is reported" test; dropping the explicit no-row branch fails the stale-targets test; removing the genuine-failure report fails the report test. **The third sabotage caught a flaw in my own test**: the mapping test's `expect(captureException).not.toHaveBeenCalled()` was only true because the tests above it happened not to report — order-dependent, not self-contained. It now clears the spy itself.
