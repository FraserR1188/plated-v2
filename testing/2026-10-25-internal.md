## Rectification log

### PL-059 — batch small four: sum the known, flag the incomplete

- **Severity:** Major. The numbers are wrong, and the error is always low.
- **Reported as:** found in code review. `sumBatchMacros` (`src/lib/compositions.ts`, was ~L810) applied NULL-poisons-total to sat_fat, salt, fibre and sugar. Three tins of beans with known fibre plus one spice with none on record logged the batch's fibre as NULL, and `sumBucket` then added nothing for it. The test at `compositions.test.ts:214` pinned this behaviour.
- **Root cause:** confirmed. All five carrying hops (`itemFromIngredient`, `batchItemRow`, `productFromItem`, `draftsFromBatch`'s `scaledNullable`, `mealEntryToProduct`) keep NULL correctly. The loss happened only in the sum.
- **Fix:**
  - For each small-four nutrient, sum the known ingredients. If any ingredient is unknown, list the nutrient in the new `meal_entries.incomplete_nutrients` (a lower bound). If all are unknown, store NULL and don't list it. A real 0 counts as known. NULL means complete, never `{}`.
  - The flag is carried by both insert sites, every copy builder, the bundle snapshot (`meal_composition_items.incomplete_nutrients`) and bundle apply. It is never in `MealEntryPatch`, so a grams edit rescales the values and keeps the flag.
  - Trends treats a flagged row as incomplete.
  - `whoop_cycle_nutrition.*_known_meals` stops counting a flagged meal as known. Without that, a partial cycle would have read as complete.
  - UI: "≥" on the edit-screen tile with one muted line; "≥" on Today's small-four day-total bars; "Fibre missing for: …" on BatchEditor and RecipeConfirm.
- **Where:** `eb21dfa`, `ad4e232`, `c939ae8`, `0c1637b`, `5cd9a1e` on `feat/incomplete-nutrients`.
- **Local checks:**
  - **Measured.** Red run without `it.fails`: 1435 tests, 25 failed for the predicted reasons (poisoned NULL or missing flag), 1410 passed. After the fix: 1435/1435. After the UI commit: 1451/1451. tsc 0 at every commit.
  - **Measured.** Nine sabotages, each caught by its intended test:
    - logic: poison restored; unknown coalesced to 0; `applyEntries` key dropped; `{}` written for a complete batch; `draftsFromFeedEntry` flag dropped (tsc also catches this one);
    - UI: 0 treated as missing; day bucket ignores flags; `addBuckets` drops pending's flags; `mealEntryToProduct` drops the flag.
  - **Measured.** `20261025120000_rig.sh` (postgres:16, stub tables): content hashes are equal before and after, and 0 rows are flagged. The sabotage inserts `{}`, `{protein}`, `{fibre}` with fibre NULL, and `{NULL}` are each refused by the named constraint on both tables, and a valid `{salt,fibre}` row is accepted. Dropping each constraint lets exactly its own cases through.
  - **Measured.** `20261025130000_rig.sh` (the real `whoop_cycle_nutrition` and `whoop_correlation` built on stubs):
    - F1–F9c pass. With no flags, the new view equals the old row for row.
    - Reverting to `count(m.x)` fails F1/F1b/F6/F6b/F9c.
    - Dropping `security_invoker` fails F8/F9/F9b/F9c: `CREATE OR REPLACE` loses the option, and user A reads user B's cycles.
    - `whoop_correlation` picks up the new counts with no change of its own.
  - **Predicted.** The hosted verification SQL (`verify/20261025120000_verify.sql`, `verify/20261025130000_verify.sql`) has not been run.
- **Manual test checklist (device, after migrations + OTA):**
  1. Make a batch with three ingredients that have fibre and one without (e.g. ground cumin with no fibre on record). BatchEditor shows "Fibre missing for: ground cumin" above the ingredient list.
  2. Log a portion. Today's Fibre bar reads "≥ n". The row in `meal_entries` has `incomplete_nutrients = {fibre}` and fibre equals the known share.
  3. Open the entry. The Fibre tile reads "≥ n g", with "Some ingredients have no fibre data" under the grid.
  4. Change its grams and save. The value rescales and `incomplete_nutrients` is unchanged.
  5. Copy it to tomorrow (copy-a-day and Copy to…). Both copies keep `{fibre}`.
  6. Save it into a bundle, then apply the bundle. The `meal_composition_items` row and the new entry both keep `{fibre}`.
  7. From a second account that follows this one, copy the entry. The copy keeps `{fibre}`.
  8. A batch where every ingredient knows fibre logs `incomplete_nutrients` NULL, not `{}`, and shows no "≥".
  9. Scan a recipe with an ingredient missing salt. RecipeConfirm shows "Salt missing for: …" above "Add to batch".
  10. Trends for that day draws fibre hollow.
- **Known follow-ups (no new IDs):**
  - **CSV export:** `csv.ts` writes a lower bound as a plain number with no marker. Whether to add a column, a marker or nothing is a separate decision: people key spreadsheets on the pinned header.
  - **`saveIngredient` leak:** `saved_ingredients` has no flag column. The only caller today is the create path, which never receives a flagged product, so nothing leaks now. A future "log again from this entry" path would save a lower-bound rate as if it were complete.
  - Existing batch entries with NULL fibre or salt can't be recomputed (`meal_entries` has no link back to the composition). They are not backfilled; only re-applies after the release are fixed.

### PL-061 — Today's small-four day totals show unknown as 0

- **Severity:** Major
- **Reported as:** found in code review during PL-059. `sumBucket` (`src/lib/entries.ts`) correctly skips NULL rows and keeps an all-NULL bucket NULL. TodayScreen then coalesces at display (`summary.towardGoal.fibre ?? 0` in the macro strip and the MacroBars; `roundSalt(summary.towardGoal.salt ?? 0)`). A day where every entry is unknown for a nutrient shows "0 g". A day with some unknown entries shows the known sum with nothing marking it as partial, although Trends draws the same day hollow.
- **Root cause:** confirmed in code. PL-059's "≥" covers only flagged lower bounds, not plain NULL rows, deliberately.
