### PL-039 — The time chip rolls a forward plan back to yesterday, saved as eaten

- **Severity:** Major. It writes a meal onto the wrong day as eaten, silently, and everything downstream of `eaten_at` inherits that: the day's totals, History, and the WHOOP correlation, where a `planned = false` row counts as evidence on the wrong cycle. The only cue is the date chip changing to "Yesterday".
- **Reported as:** Found in code review while answering PL-036, whose user journey is "plan tonight's big meal at lunchtime". Not observed on a device.
- **Root cause:** Confirmed from the code.
  - On ProductScreen, for today, when not editing and with the date chip untouched, `dayIsExplicit` is false ([ProductScreen.tsx:425-426](../src/screens/ProductScreen.tsx)). `onTimeChange` then calls `resolveEatenAt(h, m)` with no day ([:484-487](../src/screens/ProductScreen.tsx)).
  - That function subtracts a day whenever the pick is more than 3 h ahead ([time.ts:144-150](../src/lib/time.ts)). At 12:00, picking 19:00 gives yesterday 19:00.
  - The heuristic exists for one real case: logging last night's dinner shortly after midnight. It has been reachable in this shape since `61df42e` (2026-07-13); the roll-back itself dates from `622ee62` (2026-07-08).
  - Route A is unaffected: picking the time on Today's "+" picker goes through `sameTimeOnDay`, which never rolls back ([TodayScreen.tsx:758-767](../src/screens/TodayScreen.tsx)).
- **Fix:** Done on master (`ba9b8f8`), device-passed 2026-09-25 and shipped by OTA — see below. The rule was amended on 2026-09-25 before implementation. The first version kept the 3 h threshold inside the small hours, which left the same trap there: at 00:30, this morning's 07:00 went to yesterday.
  - **The rule** (`shouldReadAsYesterday`, pure, takes `now`; [time.ts](../src/lib/time.ts)):
    - with an explicit day, never roll back;
    - when the local hour is 4 or later, a forward pick is always today, and the trigger decides planned;
    - when the local hour is below 4 and no day was given, take the nearer of today's and yesterday's reading of the pick, with an exact tie going to today.
  - **One constant:** `SMALL_HOURS_END_H = 4`. The window is inclusive of 03:59 and exclusive of 04:00, and it reads the local **hour**, so the clock-change nights keep a 04:00 wall-clock cut-off. `ROLLBACK_H` is gone; nothing else referenced it.
  - `resolveEatenAt` gains a `now` parameter, defaulting to the device clock. ProductScreen's `onTimeChange` passes it explicitly.
  - **CLAUDE.md** is corrected in the same commit. The `planned` wording now reads `eaten_at > now() + 30 minutes` (a later meal today is planned), and the roll-back rule describes the window and nearest-reading rule.
  - **Other callers are unchanged.** Every other caller passes an explicit day: `sameTimeOnDay` and everything built on it, and `handleSubmit`'s `resolveEatenAtAndDate`. Today's bulk "Set time" (`retimeEntries`) doesn't use `resolveEatenAt` at all.
  - Separate from PL-036, in separate commits.
- **Detection (read-only):** see "PL-039 — detection query" below. **Run 2026-09-26.** The results, the git history check they depend on, and the interpretation are in "Detection results — 2026-09-26", below the query. In short: 19 candidates, of which 13 are ruled out by the estimated flag, leaving at most six, all Robbie's, which read as catch-up logging. **No rows repaired** (see Deliberately not changed). **Re-run Q2 on or after 2026-10-03.** **The query pre-dates the amended rule:** rows logged before 04:00 are in the `small_hours_intended` bucket, but the old code also wrongly rolled back small-hours picks of *this morning* (for example 00:30 → 07:00), so that bucket can contain bug rows too. ### PL-041 — The PL-028 cucumber repair values aren't raw cucumber

- **Severity:** Major. It's wrong numbers in stored history, written by a repair.
- **Reported as:** Found during PL-035's live OFF probe (2026-09-25). OFF's row for Sainsbury's cucumber `5010251733911` reports 52 kcal, 2.1 g protein and 8.5 g carbs per 100 g.
- **Root cause:** Confirmed that the repair used those values. **Not yet confirmed which rows carry them.**
  - The PL-028 repair's source table has `('5010251733911', 52, 2.13, 8.47, 0.37, 0.12, 0.04, 2.0, 5.57)` "from OFF" ([20260920_pl028_zeroed_nutrition.sql:106-107](../supabase/repairs/20260920_pl028_zeroed_nutrition.sql)). Scaled to 50 g, that's 26 kcal ([2026-09-20-internal.md, "Repaired values, per row"](2026-09-20-internal.md)).
  - CoFID and USDA both put raw cucumber near 10–15 kcal per 100 g, so the two repaired days likely overstate intake by roughly 20 kcal each.
  - **The process point matters more than the number.** A repair sourced from a single crowd-sourced OFF row is a fabricated measurement with a citation attached.
  - The same repair also took the Fibre & Protein Bar (`5060853641220`) from a single OFF row. Those values do reconcile by Atwater (23·4 + 34·4 + 11·9 + 19·2 = 365 against the stated 365), but that shows the row is internally consistent, not that it's this product. It's the same process risk, with lower suspicion.
- **What it would take to identify the affected rows (no changes made):**
  1. **Rows the repair wrote.** `maintenance.pl028_repair_backup` holds every row the repair could match, with pre-repair values and `row_id` ([backup columns](../supabase/repairs/20260920_pl028_zeroed_nutrition.sql)). Filtering on `barcode = '5010251733911'` lists them: 2 `meal_entries` and 1 `saved_ingredients` on `a8435663`, per the repair record. The backup is reachable as `postgres`/`service_role` only, so run it in the SQL editor.
  2. **Rows descended from them since 2026-09-20.** The repaired **library row** now carries 52 kcal/100 g, so every re-add since then inherits it. Every copy path carries `barcode` through: copy-a-day, copy-a-section and the social copy ([entries.ts:195-196](../src/lib/entries.ts), [:270-271](../src/lib/entries.ts), [social.ts:673-674](../src/lib/social.ts)), and so do bundle items ([compositions.ts:514-515](../src/lib/compositions.ts)). So a barcode query across `meal_entries`, `saved_ingredients` and `meal_composition_items` finds them. **Batch outputs are the exception:** a merged batch entry has no barcode. A batch built with this cucumber is found through its `meal_composition_items` row, and the batch's logged portions then need tracing by composition.
  3. **Group by `user_id` before reading anything.** A social copy could have put the repaired values in another person's log. The PL-028 lesson applies: grouping by a value is a join on that value. Another user's rows aren't evidence and aren't ours to correct.
  4. **Choose a documented source before any repair.** CoFID 13-523 (Cucumber, raw, flesh and skin) is already in `core_ingredients`, or a photo of the pack's label. Record why. Per the standing rule, **no repair from a single OFF row.**
  5. **A second repair changes history again.** Record the before and after per day, as the PL-028 repair did.
- **Identification queries (SELECT only, run as `postgres` in the dashboard):**

  ```sql

  select 'meal_entries' as t, left(user_id::text, 8) as user8, id::text as row_id,

  from public.meal_entries where barcode = '5010251733911'

         name, null, null, null, cal_per100, cal_per100, null
  from public.saved_ingredients where barcode = '5010251733911'
  union all
  ```

### PL-048 — `eaten_at_estimated` is true almost everywhere, so `has_estimated_times` discriminates nothing

- **Severity:** Minor (proposed; **revisited 2026-09-26, unchanged**). The reframing makes this a **definition gap, not a coding error**: the flag faithfully records what the code says it records, and what's missing is an agreed meaning. That changes the *kind* of fix (a decision first, then code), not the size of the harm. No total, date or WHOOP pairing moves, so the numbers-moved test still says Minor. The Major condition below still stands: it becomes Major if anything acts on `has_estimated_times`.
  - **Why not Major:** no total, no date and no WHOOP pairing moves. What's lost is one provenance signal: whether a meal's time was chosen or defaulted. That signal feeds a quality flag, not a number a user reads.
  - **When to raise it to Major:** if anything *acts* on `has_estimated_times`, such as a filter, an exclusion or a caption that tells the user their cycle's data is uncertain. Then every cycle is being treated as uncertain, and the correlation is quietly degraded or mislabelled. Checking for such consumers is the first step when this is taken up. It's deliberately not done here.
  - **Worth knowing either way:** a fix going forward can't repair history. A stored `true` can't be told apart as "defaulted" or "chosen, but flagged anyway", so the existing rows stay ambiguous.
- **Reported as:** Found in code review during PL-039, then confirmed on data by Robbie. **All ten of the most recent rows on his account carry `eaten_at_estimated = true`, including ordinary logs.** The query was run 2026-09-25 14:12 BST.
- **Root cause:** Confirmed from the code.
  - ProductScreen writes `eaten_at_estimated: isPlanned ? true : !timeTouched` ([ProductScreen.tsx:648](../src/screens/ProductScreen.tsx) at `fe2a3bd`; it has moved with each ProductScreen change since, and the rule dates from `61df42e`, 2026-07-13).
  - So a **planned** meal is always flagged estimated, however deliberately its time was picked.
  - A time chosen in **Today's "+" picker** also counts as estimated, because `timeTouched` only tracks ProductScreen's own time chip.
  - The route most users take (Today's picker, then save) therefore always writes `true`.
  - **The column is `NOT NULL DEFAULT true`** (measured, PL-039 Q0, 2026-09-26). A row inserted without the flag is estimated whatever the client meant. Both app insert paths send it explicitly (`addEntry` and `applyEntries`), so the default only fires for inserts from outside the app.
- **What the flag actually encodes.** It doesn't mean "this time is a guess". On the create path it means **"the time wasn't set on ProductScreen's chip"**, so a row timed through Today's picker is flagged estimated even though the user chose the time deliberately. The post-insert paths follow a different rule: an edit on a touched time, a bulk "Set time" to a past time, and a corrected confirm all clear it. So the fix isn't making the flag meaningful. It's **deciding what it should mean**, then making every write path agree. `has_estimated_times` is built on the flag as it stands today.
- **Why it matters:** `whoop_cycle_nutrition` computes `coalesce(bool_or(m.eaten_at_estimated), false) as has_estimated_times` ([20260831120000_whoop_cycle_nutrition_known_meals.sql:140](../supabase/migrations/20260831120000_whoop_cycle_nutrition_known_meals.sql)). One estimated meal marks the whole cycle, so with the flag true on nearly every row, `has_estimated_times` is true on effectively every cycle.
- **Open question — written down, not answered:** does confirming a planned meal clear the flag? PL-039's entry notes where to look (`confirmEntries`), but it hasn't been traced.
- **Fix:** Not decided.

## PL-039 — detection query

Read-only, not yet run. It's for the user to run in the dashboard, to see the scale before anything is repaired.

**Run Q0 first.** `meal_entries` has no tracked CREATE TABLE. The brief asked for "`created_at`", but the table's creation timestamp is **`logged_at`**: set at insert by `addEntry` ([useStore.ts:904](../src/store/useStore.ts)) from the client clock, and typed "when the ROW was created" ([types/index.ts:159](../src/types/index.ts)). Q1 and Q2 key on it, and Q0 confirms it exists. If Q0 shows no `logged_at` but does show `created_at`, substitute it.

**What the bug leaves behind.** A pick at local time *T* for clock time *P*, with *P* more than 3 h after *T*, is stored as yesterday at *P*. So:

- the eaten day is exactly the day before the day it was logged;
- the eaten clock time is more than 3 h later than the logged clock time;
- `planned = false`.

Only `addEntry` can produce it, because ProductScreen is the only caller, so copy, bundle and batch rows are excluded. The threshold used below is **2 h, not 3 h**: `logged_at` is taken at save, not at the pick, so a user who spent a few minutes on the screen after picking would otherwise be missed.

**What it can't separate.** A user who deliberately set the date chip to Yesterday and then picked a later clock time leaves an identical row. Treat the result as a **ceiling**, not a count.

- The `small_hours_intended` bucket, logged before 04:00, is the case the heuristic exists for, and it stays correct under the new rule.
- The `likely_bug` bucket is the population to look at.
- Times are read in `Europe/London`. A user logging in another time zone would be misread.

```sql
-- PL-039 Q0: confirm the columns Q1/Q2 rely on (meal_entries has no tracked CREATE TABLE).
-- Expect 11 rows. If logged_at is missing, stop and check for created_at.
select column_name, data_type, is_nullable, column_default
from information_schema.columns
where table_schema = 'public' and table_name = 'meal_entries'
  and column_name in ('id', 'user_id', 'name', 'source', 'meal_type', 'date',
                      'eaten_at', 'logged_at', 'planned', 'confirmed_at',
                      'eaten_at_estimated')
order by column_name;

-- PL-039 Q1: candidate rows, newest first.
with m as (
  select e.id, e.user_id, e.name, e.source, e.meal_type, e.date,
         e.eaten_at_estimated, e.confirmed_at,
         (e.eaten_at  at time zone 'Europe/London') as eaten_local,
         (e.logged_at at time zone 'Europe/London') as logged_local
  from public.meal_entries e
  where e.planned = false
    and e.source not in ('copied', 'bundle', 'batch')   -- applyEntries paths never use the time chip
    and e.logged_at >= '2026-07-08'                     -- 622ee62, the roll-back's first commit
),
c as (
  select m.*,
         round(extract(epoch from ((eaten_local + interval '1 day') - logged_local)) / 3600.0, 2)
           as hours_ahead_at_save,
         case when extract(hour from logged_local) < 4
              then 'small_hours_intended' else 'likely_bug' end as bucket
  from m
  where eaten_local::date = logged_local::date - 1
    and (eaten_local + interval '1 day') > logged_local + interval '2 hours'
)
select bucket, left(user_id::text, 8) as user8, id, name, source, meal_type,
       date, eaten_local, logged_local, hours_ahead_at_save,
       eaten_at_estimated, confirmed_at
from c
order by bucket, logged_local desc;

-- PL-039 Q2: the scale — per account and bucket.
with m as (
  select e.user_id,
         (e.eaten_at  at time zone 'Europe/London') as eaten_local,
         (e.logged_at at time zone 'Europe/London') as logged_local
  from public.meal_entries e
  where e.planned = false
    and e.source not in ('copied', 'bundle', 'batch')
    and e.logged_at >= '2026-07-08'
)
select left(user_id::text, 8) as user8,
       case when extract(hour from logged_local) < 4
            then 'small_hours_intended' else 'likely_bug' end as bucket,
       count(*) as rows,
       min(logged_local)::date as first_logged,
       max(logged_local)::date as last_logged
from m
where eaten_local::date = logged_local::date - 1
  and (eaten_local + interval '1 day') > logged_local + interval '2 hours'
group by 1, 2
order by 1, 2;
```

**Reading a `likely_bug` row.**

- `hours_ahead_at_save` between about 3 and 12, with `logged_local` in the daytime, is the lunchtime-plans-dinner pattern.
- `meal_type` may disagree with `eaten_local`'s hour. The section was derived from the time Today's picker was *opened*, not from the rolled-back time, but the user may have changed the chip, so it's a hint, not proof.
- **Nothing is to be repaired until the scale is known and each row's intent can be told apart.**

### Detection results — 2026-09-26

  - That's the shape of **catch-up logging**: logging yesterday's food the next morning. It's the false positive the ceiling caveat predicted.

**History check — READ from git, 2026-09-26.** The interpretation below depends on one rule holding throughout the window (rows logged 2026-07-25 to 2026-09-25). It does.

- **The expression.** `eaten_at_estimated: isPlanned ? true : !timeTouched` was introduced by `61df42e` (2026-07-13, "plan meals for future days"). It replaced `!timeTouched`, from `e59d877` (2026-07-12, when the flag was added), and the two agree for any past-landing row. `git log -S` finds no other commit that adds or removes it. The only other commit touching that line in the window, `5abcbcb` (2026-09-19), re-indents it into a `try` without changing it.
- **The roll-back path.** `resolveEatenAt(h, m)` with no day has been called only from `onTimeChange`, which sets `timeTouched` true before resolving. That's the same shape at `e7a7ac7` (2026-07-15) and at `8eb2e5e` (2026-08-26). `3a4e83e` (2026-08-30) moved the picker's cancel guard into the `DateTimeField` wrapper, so a cancel still never sets `timeTouched`. The semantics are unchanged.
- **Nothing writes `true` after insert.** The only post-insert writers set `false`:
  - the edit path, on a touched time;
  - `retimeEntries`, for a past time;
  - `confirmEntries`, on a corrected time, for planned rows only.

  So a row whose flag reads `true` today was inserted `true`. The create path always sends the flag explicitly (`useStore.ts:932`), so the column default of `true` doesn't fire for app inserts.

**INTERPRETATION** (from the code and the measurements above, not a measurement itself):

- **The 13 `true` rows cannot be roll-back rows.** On the create path, `false` was written for a past-landing row only when ProductScreen's time chip was touched, and that's the only route the roll-back could fire on. A previous-day row inserted `true` had its day set explicitly, from Today's page for that day or the date chip, and the roll-back was never involved.
- **That narrows 19 candidates to at most six, all Robbie's.** The other account's single row (`1dd0fc98`) is a deliberate entry.
- **The six remain ambiguous.** A `false` row is consistent with the roll-back, but equally with a time chip touched on yesterday's own page, or with a later edit or retime. All six read like catch-up logging: logged at 05:28–06:30 for the previous day's breakfast or lunch. The data can't separate the two cases.

**Re-run in a week (on or after 2026-10-03).** Run Q2 again. `last_logged` for `a8435663` should still be **2026-09-25**, since the fix shipped by OTA on that date. **If it moves, the fix didn't take**, or a new route reaches the roll-back. Investigate before anything else.
