## Rectification log

### PL-037 — Can't change an entry's meal when editing

- **Severity:** Major. The only workaround is delete and re-log. From the code, that moves `eaten_at` to "now" unless the user sets the time back, and marks the time as estimated. The mis-log also silently moves the entry between Today's sections.
- **Reported as:** "I accidentally logged a snack as breakfast and wanted to change it" … "I had to delete and re-log it as I couldn't just select it as I could when I logged it."
- **Root cause:** Confirmed from the code.
  - ProductScreen renders the four meal chips on create only. In edit mode it shows a read-only pill ([ProductScreen.tsx:792-819](../src/screens/ProductScreen.tsx)).
  - The comment justifying that says `MealEntryPatch` has no `meal_type` field ([ProductScreen.tsx:282-285](../src/screens/ProductScreen.tsx)). **It does** ([useStore.ts:83](../src/store/useStore.ts)). The restriction rests on a stale belief, not an invariant.
  - Simply adding the chips isn't enough. The edit path's patch always resends `serving_g`, all eight macros and `eaten_at` ([ProductScreen.tsx:528-551](../src/screens/ProductScreen.tsx)), so a slot change would snap every macro to the rounding grid (PL-010).
  - **Contributing cause:** `sectionForTime` never returns `snacks` ([time.ts:279-285](../src/lib/time.ts)). A snack logged before 12:00 always defaults to Breakfast unless the chip is tapped, which is exactly this mis-log.
- **Fix:** Done on master, not device-passed.
  - **The same four chips in edit mode.** They're inline in ProductScreen's header; `CopyTargetPicker` (CopyConfirm, Today's copy sheet) is a separate component and is unchanged.
  - **`buildEditPatch(original, edited)`**, pure, in `src/lib/entryEdit.ts`, returning `MealEntryPatch`, so `date` and `planned` stay unrepresentable. It diffs against the **row as loaded**: a snapshot of the store row taken when ProductScreen mounts, not route params, which a refetch can make stale.
    - `meal_type` is sent when the chip differs.
    - `eaten_at` is sent when the resolved time differs at **minute** precision.
    - `eaten_at_estimated: false` is sent only when the time chip was touched and the row still says true. It's never set to true on this path.
    - `serving_g` and the eight macros are sent only when the serving differs by value. The text is parsed, and the stored side goes through `Number()`, so a value arriving as a string can't make every edit look changed.
  - **Nothing changed → no write.** `{}` pops without calling `updateEntry`.
  - **Row missing from the store at mount → no write.** Submit says "Couldn't find this entry" and stays, rather than guessing a baseline.
  - It goes through the existing `updateEntry`, so there's no new update site. `date` is derived there only when `eaten_at` is sent, so a slot-only patch leaves the day alone.
  - **The delete dialog names the row's stored slot** (`originalEntry.meal_type`), not the chip. With the chips live on edit, the chip can differ from where the row is, and a destructive prompt must name where it really is.
  - The stale comment ("MealEntryPatch has no field for it") is replaced, and PL-010's "known bug" comment in `handleSubmit` is narrowed to what's still true.
  - The now-unused `mealPill` styles are removed.
  - Only the edited row moves: `meal_entries` rows carry no group id, and bundle items are independent snapshots by design.
- **Closes PL-010 for every edit that doesn't change the serving.** Macros are recomputed only on a serving change, which still snaps once onto the rounding grid, as it always did.
- **Deliberate side effect: an untouched time keeps its seconds.** `handleSubmit` resolves the time to the minute, and the old patch always sent it, so **every edit used to zero the row's seconds**. Comparing at minute precision means an untouched `eaten_at` is equal and isn't sent.
- **Checks against the triggers** (READ, not run):
  - The `planned` freeze trigger holds `planned` on any update.
  - `no_future_logged` only refuses a logged row whose `eaten_at` ends up more than 30 min in the future. A slot-only patch doesn't move `eaten_at`, so it passes on a past logged meal and on a planned one alike.
- **Local checks (measured = predicted):**
  - Baseline: 998/998.
  - Red commit `7801f20`: 11 new tests, **9 failed, 1000 passed**. Each failure came from the unwired stub's always-resend patch. The NULL test and the type test passed by design. `tsc` was 0.
  - Fix: **1009/1009, `tsc` 0.** `mealEntriesInsertSites.test.ts` is 8/8 and unchanged.
  - Fingerprints unchanged: Android `c1907ba4…`, 0 of 158 sources differ; iOS `5359dcce…`, 0 of 142.
- **Sabotage runs.** Each expected set was written down before running, each run matched it, and each restore was byte-identical:
  1. **Always include the macros:** 7 failed. That's slot-only, time-only, date-only, nothing-changed, seconds, "37.50" and string.
  2. **Drop `meal_type`:** 3 failed. That's slot-only, slot+serving and seconds.
  3. **Set `eaten_at_estimated: true` on an untouched time:** 8 failed, every untouched-time case that asserts its key set. **Time-only passes by construction**, because it touches the time. Its untouched counterpart, the date-only test, fails.
  4. *(Extra)* **A strict compare without `Number()`:** 1 failed, the string test.
  5. *(Extra)* **Millisecond precision:** 7 failed, every untouched-time case against a row with seconds.
- **Device checklist** (for Robbie's pass; record the SHA it ran on).

  `meal_entries` has no `updated_at`, so **`xmin`** is the write detector. It changes on every UPDATE, including one that rewrites identical values. Run the same SELECT before and after each step, and compare.

  Run this first to find a row:

  ```sql

  from public.meal_entries
  where user_id = '<your user id>' and date = '<the day>'

  ```

  Then this, before and after each step:


  1. **Change only the slot** on an existing entry (for example Breakfast → Snacks) and tap Update entry. **After:** `xmin` changed and `meal_type` changed. `serving_g`, all eight macros, `date`, `eaten_at` (including its seconds) and `eaten_at_estimated` are identical to before.
  2. **Change only the serving.** **After:** `serving_g` is new and the macros are recomputed for it. `meal_type`, `date` and `eaten_at` are identical.
  3. **Open an entry, change nothing, tap Update entry.** **After:** `xmin` is **unchanged**, so no write happened at all.
  4. **Change the slot on an entry from an earlier day** (open a past day on Today, then the entry). **After:** `meal_type` changed; `date` and `eaten_at` are identical, so the day didn't move.
  5. **Change the slot on an entry whose small four are NULL.** Before, confirm `sat_fat`, `salt`, `fibre` and `sugar` are NULL. **After:** still NULL, not 0; only `meal_type` differs.

### PL-038 — Sign-up has one password field

- **Severity:** Minor. Nothing is lost: a mistyped password can be recovered through Forgot password, which exists end to end in the app code (since `5dde876`, 2026-08-26). The email send and the `platedapp.uk` bridge are outside this repo and not device-checked here.
- **Reported as:** "Have two password input sections for confirmation of correct password" … "There was only one."
- **Root cause:** The password field has `secureTextEntry` and nothing else ([App.tsx:589-595](../App.tsx)): no show/hide toggle, no `autoComplete`, no length hint. Google and Samsung autofill therefore can't recognise it as a new-password field and offer a generated password (PREDICTED). The 6-character minimum is enforced only by the server on sign-up, but locally on the reset screen.
- **Fix:** Agreed 2026-09-25, not started.
  - A show/hide toggle.
  - `autoComplete="new-password"` on sign-up and `"current-password"` on sign-in; `autoComplete="email"` on the email field.
  - A shared length rule (one constant, used by both sign-up and `ResetPasswordScreen`), with an inline hint.
  - **Not** a confirm field. See Deliberately not changed.

- **Shipped in:** — (predicted OTA-eligible on both platforms)
- **Verified:** No.
- **Status:** Logged

## Deliberately not changed

| ID | Feedback | Why not |
|---|---|---|
| PL-038 | A second, confirm-password field at sign-up | Decided 2026-09-25. A show/hide toggle catches the same typo by letting the user *see* what they typed, without making everyone type it twice. A confirm field works against password managers: a generated password fills one field and leaves the user to retype an unseen long string into the other. With `autoComplete="new-password"`, Google and Samsung autofill can generate and save the password, which removes typing altogether. A mistyped password is recoverable through Forgot password, so the confirm field protects against nothing the reset flow doesn't already cover. The unrecoverable sign-up error is a mistyped **email** while Confirm email is off; that's a separate decision (P-TF01a), not part of this fix. |
