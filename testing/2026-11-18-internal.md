## Rectification log

### PL-062 — My Library keeps no provenance

- **Severity:** Minor. Attribution is imprecise, and `meal_entries.source` misdescribes re-added food. Since PL-060 the notice errs toward Open Food Facts, so no OFF data loses attribution.
- **Reported as:** found in code review during PL-060's investigation (`2026-10-25-internal.md`, PL-060 block, a and b).
- **Root cause:** confirmed in code.
  - `saved_ingredients` has `barcode` and `off_id` but no source and no custom-food link.
  - `saveIngredient` (`src/store/useStore.ts`) runs after EVERY create-path log in ProductScreen, including AI photo estimates and custom foods.
  - `savedIngredientToProduct` (`src/lib/library.ts`) builds a product with no `source` and no `custom_food_id`.
  - ProductScreen then picks the entry's `source` from what's left: `"barcode"` when the library row has a barcode, otherwise `"search"`. So a custom food with a barcode, re-added from My Library, logs as `"barcode"` with no `off_id` and no `custom_food_id`. An AI estimate or a barcode-less custom food logs as `"search"`.
  - Hosted data, 2026-11-18: 79 `barcode` rows with a barcode but no `off_id` or custom link, and 29 `search` rows with neither. Both groups have rows up to this week. Neither group is proven to be custom or AI (verification SQL in PL-060's block). No code path writes OFF data without its `off_id`.
- **Fix:** — Needs a `saved_ingredients` migration that adds provenance, for example a nullable `source` and `custom_food_id`. It has to be written by `saveIngredient` and carried by `savedIngredientToProduct` into the product's source and custom link. Existing library rows can't be backfilled with certainty; they would stay "unknown, treated as OFF".
- **Where:** —
- **Status:** Logged

### PL-063 — WHOOP 'Z' offsets blank local_date all winter

- **Severity:** Major. The Today WHOOP panel showed "–" for every day since 2026-10-24, and those days had no local_date anywhere downstream.
- **Reported as:** the developer noticed the blank panel on their own account.
- **Root cause:** MEASURED in the SQL editor, 2026-11-18.
  - WHOOP sends `timezone_offset` as `'Z'`, not `'+00:00'`, whenever the user is on UTC. The developer's `whoop_cycles` held 99 `+01:00`, 5 `+02:00` and 25 `Z`; the first `Z` cycle starts 2026-10-24 19:34:54Z.
  - `biometric_periods_resolved` only derives `local_date` when the wake offset matches `^[+-]\d{2}:\d{2}(:\d{2})?$` (`20260920140000_strain_updated_at.sql`), so every winter WHOOP row had `local_date` NULL. `getWhoopScoresForDate()` treats an undated row as no scores.
  - The sync itself was healthy: `whoop_connections` connected, `last_sync_error` NULL, rows upserted at 15:50 that day.
  - health-connect-ingest already normalised `'Z'` (`normalizeZoneOffsetId`, mapping.ts). The WHOOP arm never got the same fix.
- **Fix:**
  - `normalizeWhoopOffset` in `supabase/functions/_shared/whoop.ts`: `'Z'` becomes `'+00:00'`, a valid ±HH:MM(:SS) passes through, anything else is logged and written as NULL. `mapCycle`, `mapSleep` and `mapWorkout` use it; `raw` keeps WHOOP's original value.
  - `20261118170000_whoop_timezone_offset_z_backfill.sql` rewrites existing `'Z'` rows on `whoop_cycles`, `whoop_sleeps` and `whoop_workouts`.
  - Order: function deployed first, then the migration, because whoop-sync re-upserts at least 7 days on every sync and the old function would have written `'Z'` back.
- **Where:** branch `fix/whoop-z-offset` @ `81db75e` (function + 4 tests) + `742eda4` (backfill migration).
- **Local checks:** vitest 1507/1507 (uppercase path); `deno check supabase/functions/whoop-sync/index.ts` exit 0 (run with `--node-modules-dir=none`, as the repo's node_modules lacks Deno's npm deps); sabotage (remove the `'Z'` branch) fails the `'Z'` test, 1 of 15; restored byte-identical.
- **Deploy:** `whoop-sync` deployed 2026-11-18 with `--use-api` from `742eda4`'s tree. `db push` 2026-11-18: the dry run listed only `20261118170000`, and `migration list` afterwards shows it on remote. The push printed a certificate error from a post-push `@supabase/pg-delta` fetch (the same TLS interception CLAUDE.md describes for deploys); it did not stop the migration.

### PL-064 — a WHOOP connection that keeps failing refresh never escalates

- **Severity:** Major. The user silently stops getting WHOOP data and is never told to reconnect.
- **Reported as:** found during PL-063's diagnosis (developer's SQL, 2026-11-18).
- **Observed:** test account `4dbf04ae-…` has `status` `connected`, but its last successful sync was 2026-09-19 and `last_sync_error` has read `transient` since then. Its token expired 2026-09-19 and attempts stopped 2026-10-30.
- **Root cause:** confirmed in code. `getValidToken` (`_shared/whoopToken.ts`) only sets `revoked` on a recognised fatal refresh failure; every other refresh failure is `transient`, with no count or age limit. Settings shows Reconnect only for `revoked`.
- **Evidence limits:** the refresh-failure log line for 30 Oct is gone (Free plan keeps Edge Function logs about a day), and the app only ever receives "transient", so Sentry never had WHOOP's actual response. Fresh evidence: open the app once as the test account on the CURRENT whoop-sync (before PL-064 deploys) and read the whoop-sync log line within the day. Safe: if WHOOP's answer were one the current code treats as dead, the account would already be revoked. WHOOP's actual response: _pending_. If it is a dead-credential response that isFatalTokenFailure misses, that classification gets fixed too; the seven-day rule is the backstop either way.
- **Fix:** seven days agreed with the developer, 2026-11-18.
  - `refreshGivenUp` and `GIVE_UP_AFTER_MS` (7 days) in `supabase/functions/_shared/whoopToken.ts`. `expires_at` only moves on a successful refresh, so "expired more than seven days ago" means no refresh has worked for seven days. Past that, a non-fatal refresh failure goes through the existing revoke path: tokens deleted, status `revoked`, Settings shows Reconnect.
  - Where it sits: only inside `getValidToken`'s non-fatal refresh-failure branch (`"error" in refreshed`, not fatal), before the lease release. A lease RPC error, the busy wait and a failed commit after a successful rotation never reach it.
  - Our own missing WHOOP credentials never count: `whoopRefresh` now flags that error `misconfigured`, which a network failure (also status-less) is not.
  - Impact of a WHOOP outage over seven days: each user is revoked on their own next sync attempt, not all at once, and reconnects once. Revoking deletes the tokens and can't be undone; accepted because the refresh token has had seven days to recover.
- **Where:** branch `fix/pl-064-whoop-give-up` off master @ `b39a5fa`: `1d7441b` (red, 7 of 12 fail) + `c508d83` (fix). Not deployed.
- **Local checks:** vitest 1519/1519 (uppercase path); `deno check supabase/functions/whoop-sync/index.ts` exit 0 (only function importing whoopToken.ts). 12 tests in `_shared/__tests__/whoopToken.test.ts` with a fake admin client and a stubbed token endpoint, including "never revokes on a lease RPC error", busy wait, commit failure after rotation, missing credentials, and under seven days (lease released). Sabotages, each restored byte-identical: rule placed in the lease-error branch fails the lease test (1); rule placed in the busy branch fails the busy test (1); misconfigured guard removed fails 2.
- **Device check after deploy (PREDICTED):** open the app as the test account once. Its connection should flip to `status` `revoked`, `last_sync_error` `token_revoked`, its `whoop_tokens` row gone, and Settings should show Reconnect. Don't reconnect it before that check.
- **Status:** In progress

### PL-065 — WHOOP 401 mid-sync is not refreshed and retried

- **Severity:** Minor. PREDICTED impact: if the DB thinks the access token is valid but WHOOP rejects it, every sync fails until the stored expiry passes.
- **Reported as:** found during PL-063's diagnosis.
- **Root cause:** confirmed in code. `whoopGet` returns a non-fatal result on 401 with the comment "Refresh and retry", but `syncCollection` (`whoop-sync/index.ts`) maps `unauthorized` straight to `transient` and nothing refreshes or retries.
- **Fix:** — force a token refresh and retry the request once on 401; a second 401 fails as now.
- **Status:** Logged
