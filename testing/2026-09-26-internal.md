### PL-050 — `fetchEntries` truncates silently at the API's row cap

- **Severity:** Major.
  - Nothing errors. Past the cap, the oldest-logged rows just stop reaching the store.
  - Today/History show those days as empty, the 30-day CSV can come out short, and a long-pending plan can miss the confirmation banner.
  - It's the wrong-numbers class, and invisible to the user.
- **Reported as:** Found in code review. The receipt-scanner investigation (`docs/2026-09-25-receipt-scanner-findings.md`, candidate C) noted `fetchEntries` has no range while `supabase/config.toml` sets `max_rows = 1000`.
- **MEASURED 2026-09-26:**
  - User A has 787 rows, at 8.4/day since 2026-06-24.
  - At that rate A crosses 1000 around 2026-10-21, if hosted Max rows = 1000. That setting wasn't confirmed at the time of measuring.
  - **Stopgap, same day:** hosted Max rows raised from 1000 to 2000 in the dashboard (no deploy). User A now crosses around mid-February 2027.
- **Root cause:** Confirmed from the code.
  - `fetchEntries` ran `select("*").eq("user_id", …).order("logged_at", desc)` with no `.range()` ([useStore.ts:638-649](../src/store/useStore.ts) at `177ed0a`).
  - PostgREST answers that with at most `max_rows` rows and no error, so the store held the newest `max_rows` rows as if they were all of them.
  - The order also had no unique tiebreaker. A bundle apply inserts several rows with one `logged_at`, so any paging on that order alone would read tied rows twice or not at all across a page boundary.
- **Fix:**
  - Page with `.range()` until a short page returns.
  - Order by `logged_at desc, id desc`, so every row has one fixed position and pages can't overlap or skip.
  - Page size is `ENTRIES_PAGE_SIZE`, below `max_rows` and pinned there by a test that reads `supabase/config.toml`.
  - A failed page throws inside the pager. `fetchEntries` reports it once and keeps the previous list: a partial list is never installed as if complete (the PL-003 rule).
  - Local `max_rows` set to 2000 to match hosted.
- **Where:** master @ `be8ed92` (red tests + filing) + `eec75b9` (fix). Code: `src/lib/paging.ts` (`fetchAllPages`), `src/store/useStore.ts` (`ENTRIES_PAGE_SIZE = 500`, `fetchEntries`), `supabase/config.toml` (`max_rows = 2000`).

### PL-053 — `pepper` resolves to either pepper staple

- **Severity:** Minor. PREDICTED, not reproduced: a recipe line reading just "pepper" can resolve to the wrong food.
- **Reported as:** Found in PL-042's step-1 review.
- **Root cause:**
  - `bell-pepper` (`seedStaples.ts:135`) and `black-pepper` (`:155`) both carry the alias `pepper`.
  - `lookupStapleFromDb` ([ingredients.ts:281-300](../src/lib/ingredients.ts)) runs `.or(slug / aliases / display_name).limit(1).maybeSingle()` with no ORDER BY, so which of the two comes back is whatever order Postgres returns. An upsert rewrites both rows, so that order can change after any importer run.
  - **What that looks like (added 2026-09-26, after PL-042's `verify.ts` run). Read this before trying to reproduce it.** `black-pepper` is one of the 9 staples with a NULL in the big four (CoFID marks its energy N).
    - When the unordered lookup returns `black-pepper`, `stapleToProduct` returns null ([ingredients.ts:159-163](../src/lib/ingredients.ts)). Tier 2 is skipped, and the line falls to tier 3 ([:251-266](../src/lib/ingredients.ts)): OFF's top result for "pepper" is preselected, as `off-generic`, with no staple `unit_grams`.
    - When the lookup returns `bell-pepper`, the line gets the red-pepper staple, preselected as `staple`.
    - So the symptom isn't "black pepper where bell pepper was meant". It's a preselected pick that **swaps between the bell-pepper staple and whatever OFF ranks first for "pepper"**, and can change after any importer run. It comes back empty only when OFF returns nothing.
    - To reproduce, check the confirm row's source (staple against OFF), not the food name alone.
  - Separately, `bell-pepper` is CoFID's red pepper (13-524) but carries the alias `green pepper`. Green is its own row (13-318, 15 kcal against red's 21).
- **Fix:** Candidate, not started. Take `pepper` off at least one of the two staples, and move `green pepper` off the red row (drop it, or give it its own staple). Whether the lookup should also get a deterministic order is a resolver change, which belongs to PL-035.

### PL-057 — Offline cold start stays on the loading screen

- **Severity:** Major, proposed.
  - With no signal, the app can't be opened from cold: no Today, no History, not even yesterday's data.
  - PREDICTED from the code, it may then land on the sign-in screen, which reads as "you've been signed out".
  - Proposed Major rather than Blocker: nothing is lost, and it recovers once signal returns. That's the user's call.
- **Reported as:** Observed by Robbie on the production build (OTA `ced40438`, runtime `c1907ba4…`), 2026-09-26. It was PL-050's first-load check: cold start in airplane mode, and it "wouldn't go past the loading plated screen". How long it was left wasn't recorded.
- **Root cause:** **Unconfirmed; PREDICTED from the code.**
  - The screen is App's own JS splash ([App.tsx:389-398](../App.tsx)), held while `loading || !fontsLoaded`. The JS bundle loaded, since that screen is JS.
  - `loading` is cleared in one place only: the `onAuthStateChange` callback ([App.tsx:117-150](../App.tsx)). That gate has been in `App.tsx` since the initial commit (`c3f9cfa`, 2026-06-06).
  - In auth-js 2.108.0, the first callback (`INITIAL_SESSION`) waits for `initializePromise`. If the stored access token is within 90 s of expiry, or already expired, initialisation tries a refresh first.
  - A refresh retries network failures with backoff (200 ms, doubling) for up to a 30 s budget ([GoTrueClient.js:3842-3867](../node_modules/@supabase/auth-js/dist/module/GoTrueClient.js)). A retryable failure keeps the stored session.
  - `_emitInitialSession` then loads the session again, finds it expired, and refreshes again (up to about 30 s more). On failure it emits `INITIAL_SESSION` with `null` ([:3505-3521](../node_modules/@supabase/auth-js/dist/module/GoTrueClient.js)).
  - **Expected offline, with a stale token: about a minute of splash, then the sign-in screen**, even though the session is still in storage. With a fresh token (more than 90 s left), it should open at once.
  - Access tokens live about an hour, so any cold start after an hour away takes the stale path.
  - Two things are not ruled out: fonts (`useFonts` on bundled assets, PREDICTED fine offline), and `fetch` hanging rather than failing fast in airplane mode, which would make the wait unbounded.
- **Measure before fixing:**
  - (a) Open the app online, force-stop it, then within 30 minutes cold-start it in airplane mode, so the token is fresh. Time the splash.
  - (b) Leave the app closed for more than an hour, then cold-start it in airplane mode, so the token is stale. Time the splash, **wait at least 2 minutes**, and note whether it ends on the sign-in screen.
  - (a) fast and (b) about 60 s then sign-in confirms the mechanism. (b) never ending points at a hanging `fetch` instead.
- **Measurement parked** at Robbie's request, 2026-09-26. The two timed cold starts above are carried to another session; nothing is fixed before they're done.
- **Fix:** Not decided. Direction, for discussion:
  - release the splash on the stored session without waiting for a network refresh;
  - treat a retryable refresh failure as "offline, still signed in", not "signed out";
  - let the reads' failure paths (PL-050's keep-previous) handle the rest.
  - This is also what makes PL-050's first-load check answerable.

### PL-058 — History's daily average fabricates zeros for unknown macros

- **Severity:** Major, proposed by analogy with PL-008.
  - It's a fabricated zero in a number the user reads directly, and on the same screen family where Trends shows a gap for the same day.
  - It only affects sat fat, salt, fibre and sugar. The big four are `NOT NULL` (PL-011).
- **Reported as:** Found in code review, as candidate A in `docs/2026-09-25-receipt-scanner-findings.md`. Filed on Robbie's instruction, 2026-09-26.
- **Root cause:** Confirmed from the code.
  - `HistoryScreen` maps each day's eaten bucket with `eaten.satFat ?? 0` (and the same for salt, fibre and sugar) ([HistoryScreen.tsx:66-72](../src/screens/HistoryScreen.tsx) at `7eab3a3`).
  - It then averages over every logged day ([:82-109](../src/screens/HistoryScreen.tsx)).
